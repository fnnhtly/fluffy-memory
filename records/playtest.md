## 2026-04-19 · 摩擦第五轮：查清真相 + 交给你调（runtime=html，执行者：Agent）

### 1. 之前调不动的真因（已修）

- 木框**平时根本不碰地面**（它架在轮子上，离地 0.6 m），调车壳摩擦永远没感觉；

### 2. 现在的真·地面摩擦（实测数据）

| groundFriction | 5 m/s 滑行 | 1-1 | 1-2 | 1-3 | 1-4 | 1-5 |
|---|---|---|---|---|---|---|
| 0 | 6.9 m | ✅ | ✅ | ✅ | ✅ | ✅ |

**物理事实**：木框静摩擦 μ≈0.55 → 静摩擦角 ≈29°。比 29° 缓的坡，

### 3. 结论与交付

- 关卡物理回滚到能全通（34/34）的基线：`groundFriction = 0`；
- 但把它做成了 **T 面板里的滑杆**（地面摩擦 0~8 / 木框静摩擦 0~1.5 / 轮子抓地 0.5~4），

- 保留 **1280×720 作为设计基准**（所有 HUD 像素坐标不变）

| 3 | 4:3 底部露淡黄天空 | 地形多边形只铺到 `DH+40` | 底部延伸到 `DH + VIEW_OFF_Y + 40` |
| 4 | 4:3 下 HUD 整体偏上 | HUD 用固定 1280×720 坐标 | build 阶段 UI 外套 `ctx.translate(0, VIEW_OFF_Y)` |

## 2026-11-13 · 用户报的真实 bug：打气筒长按一直旋转（runtime=html，执行者：Agent）

**用户反馈**：「打气筒为什么左键长按会一直旋转，不应该是点一下转一下吗」

### 根因（这是个很隐蔽的架构问题）

1. `tryPlace()` 对"已放置的同款方向件"会执行 `dir = (dir + 1) % 4`（实现"再点一次换方向"）
2. 但渲染层的**吸附高亮**和**悬停红叉预览**，是**每帧**调用 `tryPlace()` 来探测"这格能不能放"
3. → 鼠标悬停在打气筒上时，每帧转 90°，按住不松就**一直旋转**

也就是说：**用来"问一个问题"的函数，偷偷改了答案**。

### 修法：把查询和命令分开（CQRS 思路）

| 函数 | 职责 | 副作用 |
|---|---|---|
| `canPlace(level, build, part, r, c)` | 只回答"能不能放 / 会不会转" | **无** |
| `tryPlace(...)` | 先 `canPlace`，再写数据 | 有 |

渲染层两处探测改用 `canPlace`，删掉了原来那段"探测后手动撤回"的补丁代码。

### 修复过程中又踩了一个坑

重写 `canPlace` 时漏了「**结构件（木框）可以当起点自由放置**」这条特判，
导致第一块木框就被 `connect` 拒绝 → 34/34 全线崩溃（`reason=empty`）。
补上 `if (PARTS[part].structure) return { ok: true }` 后恢复全绿。


## 2026-11-13 · 第 21 轮：帧率真相（用了两轮才发现测错了）（runtime=html，执行者：Agent）

### 上一轮的重大误判

上一轮测出 13.8 fps，以为是代码问题，费了大力气做离屏缓存（还搞坏了画面）。
**这轮发现：真正的元凶是测试脚本里的 `--disable-gpu` 参数。**

| 渲染后端 | 帧率 |
|---|---|
| `--disable-gpu`（软件光栅化） | **14 fps** |
| 默认（不限制） | **38.4 fps** |
| swiftshader | 15.2 fps |

**结论：之前 20 轮测的所有帧率都虚低 2~3 倍，因为测试环境在用软件渲染。**

### 正确的诊断方法（这轮才做对）

1. **先给 drawWorld 各阶段加计时** → 每帧只花 2.87 ms

   JS 里所有函数加起来不到 3%
3. **对比不同渲染后端** → 确认是软件渲染

如果上一轮先做第 2、3 步，就不会去写那个破坏画面的离屏缓存。

### 本轮实际优化（都是"减少填充像素"）

| 优化 | 效果 |
|---|---|
| 移除测试脚本的 `--disable-gpu`（23 个脚本） | 14 → 30.4 fps |
| 石头 108×72 → **128×86**（块数再减 30%） | |
| 碎石步长 4 → 6、草叶步长 3 → 5 | |
| （上一轮已保留）地形缓存 + DPR ≤ 1.5 | |

**最终：13.2 → 38.8 fps（3 倍）**，画面无退化（石头更大反而更接近参考视频）。

### 教训

> **测性能前先确认测量环境本身没有限速。**
> `--disable-gpu` 是我为了截图稳定性加的，结果它让所有性能数据失真了两轮。

建造期玩家是全知的，但**一点出发，信息全消失**：屏幕上只剩重量/能量/速度三个数字。
第一次玩的人不知道"这关有几个木箱""目标是旗子还是别的东西"，只能靠记忆。
参考视频里每关开始都有一屏"关卡名 + 目标"，这是正常商业 2D 游戏的基本礼仪。

### 做了什么

`launch()` 里挂 `state.runBanner = 2.0`，`drawHud()` 里画一条 104px 高的"胶片带"：

- 上下两条渐隐金线夹住中段，暗带本身也是渐隐的（`rgba(8,16,22,0 → .72 → 0)`），不是硬边色块；
- 主标题 `1-1　上坡起步`（30px 金），右侧轻微滑入 26px；
- 副行写目标，由关卡数据算：`拿 2 个木箱　·　把小猪送到终点旗`；
- 0~0.25s 淡入、1.6~2.0s 淡出，**2 秒后彻底消失**，不挡任何操作。

### 一次差点被自己骗过去的"证据"

第一版测试是这样写的：

```js
const L1 = await luma();          // 发射后 0.2s
await sleep(2400);
const L2 = await luma();          // 横幅消失后
chk('横幅压暗了画面', L1 < L2 - 3, ...);
```

跑出来 `103.1 → 202.2`，"通过"。但这个差值**根本不是横幅造成的**——
2.4 秒里车已经开出画面，场景本身全变了。真实原因是两个变量的变化混在一次测量里。

改成：先把 `paused=true` 冻结同一帧，只翻转 `runBanner`，再取亮度：

```
暗带亮度  横幅 56.8 / 无横幅 81.5      ← 这 24.7 的差才是横幅的贡献
```

并且把判据从 `差 > 3` 提到 `差 > 20`：3 的容差连噪声都能"通过"。

### 排版审计也顺带补了一个状态

横幅只活 2 秒，之前的审计根本抓不到它（每次都是等 800ms 让它消失后再审）。
现在加了 `run-banner` 状态（发射后 300ms 就审），**真正检查了那两行字**：

```
✓ run-banner  文本 4       ← 横幅期间画面上一共只有 4 条文字
✓ run         文本 11
```

### 回归

`verify.mjs` **23 项全部通过**（新增 `test_run_banner`，含 6 条断言）：

```
✓ 发射前没有横幅
✓ 发射后横幅出现                    runBanner=1.65
✓ 横幅期间画面确实被压暗（同帧对比）  暗带亮度 横幅 56.8 / 无横幅 81.5
✓ 2.4s 后横幅自动消失
✓ 横幅进行中
✓ 横幅期间点暂停仍有效
```

### 教训

> **一次测量只能改一个变量。** 第一版那个"通过"是两件事叠在一起造成的，
> 如果我没去追问"103→202 到底是谁变的"，它就会作为一条假证据留在仓库里。

顺带记一条同类：`run-banner` 这种"只活 2 秒"的状态，任何定时采样的测试都会漏掉 ——
要么在窗口内采，要么像这次一样直接翻转状态造出窗口。

## 2026-11-13 · 第 30 轮：第三把量尺 —— 文字对比度（runtime=html，执行者：Agent）

### 为什么

前两把尺子（排版审计 = 文字不越界/不压字，像素探针 = 图元画出来了）都只看**位置**。
可"看不见"还有第二种死法：**字的位置完全正确，但颜色和它背后的东西一样**。
参考视频里这种情况一次都没有 —— 商业游戏不会把米白字压在亮天空上。

### 怎么量

没法"看"截图，就让画面自己交数字。做法是给 `fillText` 加一个总开关：

```
第 N 帧：记下所有文字的包围盒 → 把 __leg.skipText 打开
第 N+1 帧：同样场景，不画字   → getImageData 得到"纯背景"
第 N+2 帧：同样场景，正常画字 → getImageData 得到"背景+字"
```

两张图逐像素求差，差值大的就是字形像素。再用 WCAG 公式算对比度：

- 小于 20px 的字：要求 **4.5:1**（AA 正文标准）
- 20px 以上（标题）：要求 **3.0:1**（AA 大字标准）

### 第一次跑：54 / 195 条不合格 —— 其中 38 条是假的

报出来的东西长这样：

```
「0」 12px  对比 3.32   fg rgb(211,136,121) / bg rgb(63,73,82)
「结构」 11px  对比 4.20  fg rgb(104,135,154) / bg rgb(22,35,42)
```

`fg rgb(211,136,121)` 这颜色在源码里根本不存在（源码是 `#ffb4a2` = 255,180,162）。
原因是**取了整个包围盒的平均**：小字有抗锯齿，边缘像素是"前景和背景混出来"的，
把这些半吊子像素平均进去，测出的前景色就被拉向背景色，对比度自然偏低。

改成**只取差异最大的前 8%（至少 6 个像素）**，也就是只取字形核心：

```
修前 54 / 195     修后 16 / 195
```

### 剩下 16 条是真的

## 2026-11-13 · 第 31 轮：选关缩略图从"一条灰线"变成"这关长什么样"（runtime=html，执行者：Agent）

### 上一轮自己记下的弱点

> 选关页的地形缩略图仍是 44px 剖面条，信息量偏低。

44px 的单色剖面在五关之间几乎是同一张图：`#` 和 `=` 都变成一个灰三角，木箱位置没有，
起终点只有两个小点。玩家点进去才知道"这关有冰面"。

### 改法：让缩略图承载三件事

1. **地形轮廓**（本来就有的）—— 加高到 56px，坡度看得出来了；
2. **地貌差异** —— 草皮颜色从 `BIOMES[].grass` 取，冰面段单独换成 `#bfe9ff` 并加**短斜线**（不靠颜色也能认）；
3. **关卡物件** —— 木箱画成小方块、起点绿点、终点是杆子 + 红三角旗，和场上同一个语言；
4. 底色用 `BIOMES[].skyTop` 的 50% 透明度做渐变，洞穴关一眼就是暗的、黄昏关一眼是紫的。

顺手把每张卡的高度算了一遍：缩略图 44→56，零件箱文字 236→240，仍在 CH=250 的卡内（底边留 10px）。

### 又一把需要校准的尺子

第一版判据是「**冰面关的缩略图应该"偏蓝"**」，阈值 12% 偏蓝像素。跑出来：

```
1-1 草地  偏蓝 88.6%      ← 判据当场失效
1-2 峡谷   偏蓝  0.3%
1-3 洞穴  偏蓝 83.3%
1-4 冰面  偏蓝 97.9%
1-5 黄昏  偏蓝 48.7%
```

草地关的天空本来就是蓝的（`skyTop: '#8FC4E0'`），所以"偏蓝"根本没有区分力。

换成「**近白像素（亮度 > 205）占比**」—— 冰面是唯一有高光的关：

```
1-1 0.0%   1-2 0.1%   1-3 0.0%   1-4 6.0%   1-5 0.1%
```

冰面 6.0%，其余全在 0.1% 以下，**差 60 倍**，这才是一把能用的尺子。

## 第 33 轮 · 界面不许自己盖自己，五关不许有不能通

这一轮的起点是一次"眼睛看不见但玩家一眼就看得见"的错误：
行驶期右上角的「?」帮助按钮，被同屏的计时面板压住了下半圈。
我先写了一个圆盘亮度探针，读数 52（建造期同一按钮 63.3）——
**这个差异只有 17%，根本不足以当判据**。换成沿圆周扫金圈：
建造期 40/72、行驶期 72/72，反而说明行驶期"更完整"，方向也是错的
（那个 40/72 是抗锯齿采样点没踩准，不是画面问题）。
真正定案的是一条几何事实：按钮 y[84,130]、计时面板 y[90,120]，
重叠 1140 px²。**"看着还行"和"几何上确实相交"是两件事，只有后者能判定。**

### 改了什么

| 位置 | 原来 | 现在 |
|---|---|---|
| 行驶期计时/木箱面板 | 硬编码在 `(DW-224, 90)` 与 `(DW-224, 126)` | 抽成 `runTimeRects()`，移到 y=138 / 174，按钮下方 8px 起 |

| 结算页键盘 | **没有分支**：按空格什么都不发生 | 空格/Enter = 重试（保留拼装）、N/→ = 下一关、L/Esc 仍可开选关 |

进度轨不是装饰。原来玩家在行驶中唯一的空间信息是"屏幕上看到什么"，
终点在 40 列的关卡外，完全无法判断还剩多远；一旦翻车也不知道

## 第 34 轮 · 先把"假红"清干净，再谈优化

这一轮真正做的事不在游戏里，在测试基建里。上一轮末尾 verify 全绿 34 项，
这一轮加了两条新断言之后，同一个 commit 反复跑出现了完全不同的结果：

| 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|
| 34/34 全绿 | 对比度 1/201 红、test_coins 崩溃 | test_resolutions 超时、test_touch_all 超时、test_perf_stable 45.6fps |

代码没动。这说明**红不是因为游戏坏了**，而是因为测量环境坏了。
查下来是三个叠在一起的原因：

1. **`child.kill()` 在 Windows 上只杀 launcher**。`spawn(msedge)` 返回的是启动器，
   真正的浏览器进程是它的子孙。所以每跑一个脚本就留一整棵 Edge 进程树。
   跑到第 15 个脚本时机器上已经有 45 个 msedge 进程，帧率自然掉、
   CDP 连接自然超时。这些红全是假的，但和真回归长得一模一样。
   修法：`tools/lib/asserts.js` 新增 `killTree()`，用 `taskkill /T /F` 杀整棵树；
   四个不走 `A.finish` 的审计脚本也单独接上。
2. **CDP 端口写死**（9412~9441，六个号被重复用）。串行跑不会撞，
   但残留进程一多就会连到别人的浏览器上——表现为"崩溃或超时"。
   修法：41 个脚本统一改成 `9400 + random(400)`。
3. **把"空闲机器基线"当成了断言**。`test_perf_stable` 原来写的是 `>= 55`，
   而同一份代码在负载下实测出现过 45.6。**一个会随机器负载随机翻红的测试，
   比没有测试更糟**——它会训练你忽略红色。

### 新的帧率判据（三条，各自有语义）

| 长帧（>33ms）比例 | < 25% | 卡顿（帧数够但一顿一顿） |
| 建造页中位帧率 | ≥ 45 | 两屏都要管 |

空闲机器基线 60.0 / 长帧 0% 写进日志，**不写成断言**。
同时用 rAF 时间戳记每一帧的间隔——"数帧数 ÷ 秒"看不出卡顿，帧间隔能。

`tools/selftest_asserts.js` 里加了一条真起子进程的自检：
`killTree` 之后 `process.kill(pid, 0)` 必须抛错。自检现在 9 项。

状态条从 `rgb(182,255,158)` 变成 `rgb(255,180,162)`，Δr=73、Δg=−75。

## 第 35 轮 · 幽灵热区，和一条与负载无关的帧率判据

### 幽灵热区：按钮删了，判定还在

读 `mousedown` 时发现 `btnRect('retryRun')` 还返回一个 84×84 的矩形
（右下 980..1064 × 500..584），`mousedown` 里也还判它 ——
但 `drawButtons()` 早就不画这个按钮了（注释写着"重开在左上，这里不再放重复按钮"）。
于是玩家在右下那片**空白**上随手一点，就会被莫名其妙踢回建造页。

这类 bug 很难靠读代码发现（判定和绘制在两处，中间隔了 1500 行），
所以我写的是一条不依赖"哪个按钮画没画"的判据：
**在行驶画面上撒 60px 网格点，凡不在任何"看得见的矩形"里的点，点下去都不许改变
phase / run / 拼装格数。** 183 个点里当时有 4 个红：(1000,520)、(1000,580)、
(1060,520)、(1060,580) —— 正是那个删掉的按钮的中心区。

修掉之后 0 个。同时加了反向对照：可见的暂停钮必须**真的**点得动
（否则"没有副作用"可能只是"点击注入根本没生效"），以及一条自证：
已删除的 retryRun 中心点 (1022,542) 必须落在所有可见矩形之外 ——
没有这条自证，"0 个副作用点"只能说明网格没撒到那儿。

### 帧率判据：改成和空转基线的比值

上一轮把阈值从 55 降到 45，这一轮它又红了（48.0 / 52.8 / 45.6 都出现过）。
问题不在阈值高低，在于**绝对帧率里混着"这台机器此刻有多忙"**。
所以改成同一次会话里先量一个基线：

1. 同一个浏览器、同一个时刻，打开一个只有空 canvas + 空转 rAF 的 data: 页面；
2. 量它的 rAF 频率当基线（实测 60.9）；
3. 判据换成 `游戏 / 基线 ≥ 0.75`。

负载被约掉了。软件光栅化事故时这个比值是 **0.23**（14 / 60），
现在是 **0.79** —— 判据有 3 倍以上的区分度，而且不再随机器忙闲翻红。
另外加了"基线本身 ≥ 25fps"的前置断言：基线都跑不满时，
比值没有意义，要先如实报出"这台机器现在不能测性能"，而不是给一个假绿。

## 第 36 轮 · 照《捣蛋猪》重做三星：累计制 + 不散架 + 让 1-2 名副其实

用户的指令是「了解参考一下，以捣蛋猪为参考模板来做」。所以这一轮先做研究，再动手。

### 研究：拿得到什么，拿不到什么

参考拆解写进 `docs/reference-badpiggies.md`。**必须如实说明来源**：
萌娘百科 + 百度百科的正文（Edge headless + CDP 取 innerText），
Wikipedia / Fandom / r.jina.ai 本机直连全部超时（`ERR_CONNECTION_TIMED_OUT`），
B 站那个视频本身也解不了（`video_probe` 报 I/O error）。

所以这一轮**没有任何一条设计结论来自"看了视频"** —— 我不能声称看过。
下面的每一条都能在两篇百科原文里找到出处。

### 差距 1：三星是累计的，我们是一局定生死

原文：「每一关的三星是采用累计的方式获得。有些关卡也许需要一次获取三星的条件，
分别三次获取也算作三星通关。」

我们原来是 `stars = 这一局满足的条件数`，存档里只有一个数字。
后果很直接：**玩家一旦没在一局里同时做到，就得整局重来**，
第三颗星从"目标"变成了"惩罚"。这跟参考的设计意图正好相反。

改成三个**永久标记**：

```js
goals = { arrive, boxes, challenge }     // 只增不减
stars = goals 里为 true 的个数
```

存档写的是 `goals`，星星数由 `starsOf(goals)` 现算；金币也从 `goals` 推导
（`coinsOf(stars, boxes)`），不再单独存一个 `coins` 字段 —— 两处数字迟早会漂。
旧存档（只有 `stars: 1`）由 `migrateRecord` 迁成 `{arrive:true, boxes:false, ...}`，
测试里专门验了这条路径。

结算页也跟着改：画的是「这一关现在一共亮了几颗」，**失败一次不会让星全灭**，
并把这一局**新点亮**的那颗标上 NEW、把还差的那几颗连同条件名字列出来。
原来那句"★★★ 条件：xxx"只说了要求，没说"你现在差哪颗"。

### 差距 2：没有 KRAK SNAP（不散架）

参考里最经典的第三星，判据是「载具不散架，**且**猪不能从载具里掉出来」。
我们的木框耐久 3 段早就做了，但一直没人在意 —— 因为没有一颗星奖励"造得结实"。

`damageCar` 加了两个标记：`hullBroken`（任一结构件碎掉）和 `pigEjected`（猪脱离载具），
`challengePass` 的 `noBreak` 分支要求**两条都不成立**。

只判前者是不够的：把猪放在最外层格子上、车一翻滚猪被甩出去，木框还完好，
但载具已经没法运猪了 —— 那不叫"不散架"。所以 `test_no_break.js`
直接构造三种坏状态（框碎 / 猪弹出 / 两者）分别断言判失败，不依赖"某一关恰好撞得碎"。

### 顺手挖出一个死代码档位

写 `noBreak` 的测试时要"真的摔碎一次"，结果发现怎么摔都碎不了。
查下去：`damageCar` 里写的是 `vn > 14 ? 2 : 1`，而 `Params.maxSpeed = 12`
给整车速度设了硬上限 —— 30 米自由落体砸地实测最大法向速度 **11.97 m/s**，
那个 2 点档**永远进不去**。

改成和真实可达速度对齐的三段（`probe_hull_break.js` 量过 400 种随机造法）：

| 法向速度 | 伤害 | 现实含义 |
|---|---|---|
| 6 ~ 8 | 1 点 | 磕一下，木框裂一道 |
| 8 ~ 11 | 2 点 | 撞狠了，接近散架 |
| ≥ 11 | 散架 | 只有从高处坠落能触发 |

平地正常跑起来最大法向速度约 2.3 m/s，所以这三档在日常通关里不会误伤 ——
改完五关的标准解仍然全绿，木框耐久都还是 3。

### 差距 3（自己发现的）：1-2 叫「按一下」，但它的三星奖励的是**不按**

1-2 的第三星原来是 `pumpPress max 0`（不许按打气筒）。可实测不按也能 2.80s 通关 ——
这一关名义上在教打气筒，实际在教"别用它"。玩家过完 1-2 仍然不知道打气筒是干什么的。

先把打气筒的能力边界量清楚（`probe_pump_power.js`）：

- 1 个朝上满蓄力 → 抬升 0.85 m（不到一格）
- 2~3 个朝上 → 约 4 m（v↑ 11.9，已经顶到 maxSpeed 限速）
- 1 个朝右满蓄力 → 水平 9 m
- 按住越久蓄力越大：0.05s→v↑2.3，0.4s→4.1，0.8s→6.0

然后试了四套改法，每一套都实测，不靠推演：

| 方案 | 不按 | 按一下 | 按下时机的成功率 | 判断 |
|---|---|---|---|---|
| 1 格硬台阶 | fail | win | 2/30 (7%) | 窗口太窄，教的是卡帧 |
| 2 格深坑 | fail | win | 6/30 (20%) | 同上 |
| 平地起步 | fail | win | 19/19 | 窗口好，但车完全不动，丢了滚动的观感 |
| **终点挪到 col 14** | **fail** | **win** | **17/39，窗口 0.2~1.9s** | **选这个** |

最后这个方案地形一个字没改：不装打气筒最远滑到 x=13.26 就停住，
终点在 col 14 —— **不按永远差那 1 格，按一下就够**。按住时长 0.1~1.2s 都行，
不用卡蓄力。第三星改成 `pumpPress max 1`（"只按一下"），名字和关卡名对上了。

### 标准解变成"可执行的"

1-2 改完之后，`SPECS['1-2']` 光有零件摆位不再能通关 —— 十几条用
`applySpec + launch` 自动跑关的测试会一起红。所以给标准解加了两个元数据字段：

```js
'1-2': { ..., _dirs: { pump: 0 }, _presses: [{t:0.8,k:'press'}, {t:1.5,k:'release'}] }
```

页面新增 `launchSpec(levelIndex, specKey)`：摆件 → 发射 → 装朝向 → 按时刻调
`pressInteract/releaseInteract`。**走的是玩家按 1 键的同一条代码路径**，不是伪造 `pumpPress`。

`test_launch_spec.js` 验四件事：能驱动 1-1/1-2 通关、1-2 的 `pumpPress` 真的 = 1、
把 `_presses` 抽掉就过不去（证明是"按"让它过的）、
浏览器里玩出来的结果和 Node 端 `simulate` 一致（没有第二套物理）。

### 结果是靠"让它能红"换来的

这一轮红了 4 项，没有一项是阈值问题，全是判据已经过期：

1. `check_html_logic.js` 说"1-1 拿满 2 星" —— 1-1 现在有第三星，应该是 3 星。
2. 同文件说"大冲击后耐久 3 → 1（掉 2）" —— 它连续调了两次 `damageCar(20)`，
   第一刀现在直接散架，第二刀打到的是已经碎掉的件，`hp=-6`。
   改成三段分开验、每段前恢复耐久。
3. `test_coins.js` 说"1-1 没有特殊条件 → challenge 标记不亮" ——
   1-1 现在有 `noBreak`，正常通关时这颗**应该**亮。
4. `test_all_levels.js` 的 1-2 判定失败 —— 它还在用 `applySpec + launch`。

另外 `test_challenge_bar.js` 里"按一下后条件不满足"这条也过期了
（现在是"按一下仍满足、按两下才不满足"），已改成两条独立断言。

对比度审计还揪出一处：结算页未点亮星的标签用了 `rgba(150,168,180,.75)`，
在深底上只有 4.37 —— 而**未点亮的标签恰恰是玩家最需要看清的**（他还差什么）。
提到 0.72 白之后 5.90。

### 现在的结果

`node tools/verify.mjs` → **39 项全绿**，27 个交互脚本。
五关标准解全部通过，1-1 从 2 星变 3 星，1-2 从"不按也三星"变成"必须按一下"。

## 第 37 轮 · 补气球和沙袋：让游戏第一次能"抬头"

方向是上一轮就定好的（参考拆解 §6 第 3 条）：**先补玩法深度，不先转 Lua**。
理由写在 `docs/reference-badpiggies.md` §6：现在五关全是"水平推过去"，
气球/沙袋是唯一能在不动机场的前提下把维度加一个的零件。

### 做了什么

| 层 | 改动 |
|---|---|
| 数据 | `PARTS.balloon` / `PARTS.sandbag`，各带 `stack: true, maxStack: 3, tapOnBody: true` |
| 规则 | `cellCount` / `consumeStack` / `recomputeLift` / `syncCarMass` 单点重算质量与浮力 |
| 物理 | `fy += G·liftMass`（先于轮子），`vy` 钳到 `Params.liftMaxRise = 2.5`；气球碰地自动破 |
| 渲染 | 气球（径向渐变 + 扎口 + 绳）、沙袋（麻布 + 束口 + 缝线）、`×n` 堆叠徽标 |
| HUD | 建造期「浮力 / 压舱 / 净重」，行驶期「气球 n · 沙袋 n · 净重 · ↑上升/↓落下」 |
| 交互 | 行驶期点车身 = 扎气球 / 扔沙袋（`RAP.tapAt`），半径 0.85 m，不占交互键 |
| 关卡 | `levels/06.json` 1-6《抬个头》+ `SPECS['1-6']` |

### 三个真正的坑（不是调参，是设计错误）

**1. 蠕行刹车把重力吃掉了。**

现象：20° 坡、6 气球 + 3 沙袋（净重 1.80 / 9.00），10 秒只挪 **2.00 米**。

一开始怀疑是气球让摩擦失效，写 `tools/probe_lift_roll.js` 量速度曲线才对上：
净重 1.80 时沿坡加速度只有 0.67 m/s²（每帧 0.011 m/s），
而 `creepBrake` 对 **1.5 m/s 以下无条件生效**，每子步抹 `2.5·(1−v/1.5)·h` ≈ 每帧 4%。
**车永远到不了 1.5 m/s，刹车永远按着不放。** 修完同一个案例滚 25.43 m、vx 5.58。

这条的教训不是"改个数"，而是：**任何全局减速都必须先问「它在斜坡上合理吗」**。
抹平地残余抖动和抹掉唯一驱动力，在代码里长得一模一样。

**2. 只判 x 的终点判据，会让"挂一堆气球什么都不做"通关。**

第一次实现是 `car.x >= goal.col` 就赢。气球车一直往上升、`vx` 还有 2 m/s，
于是它"飘过"终点线也算到（实测 `maxY = 19.9`）。
第一版修法 `goalAlt ≤ 3.0` 仍然放过了一种情况：车在终点线上空 8 米掠过，
2.7 秒后砸在终点后面的地上 —— 那时 x 早已越线，判定照样触发。

最终口径是 `越线 && |car.y − surfaceY(car.x)| ≤ 2.2 m`，
高度用**车当前的 x** 去取地表，不是终点那一格的地表。
2.2 是量出来的：五关标准解静止时车心离地 1.29–1.62 m，1-6 是 2.18。
取 2.2 是"刚好容得下所有现有关卡、刚好容不下从旗子上空飞过"的唯一值。

**3. 关卡形状被物理参数锁死了。**

先想的是最自然的形状：一条 8 格宽的深沟，抛过去。跑了 72 种组合的盲扫，
**可过窗口全是 0**。用 `tools/trace_flight.js` 打轨迹才看清原因：

上升是**定速** 2.5 m/s，而带球车水平只有 1.8 m/s →
空中轨迹斜率被锁死在 **约 1.4 : 1**。飞 8 格要升 11 米，车早出画面；
就算勉强够，窗口也只有 0.1–0.2 秒。

换成"一格沟 + 3.3 米立面墙"之后，横向只需 1 米，问题变成"纵向够不够高"，
窗口从 0.1 s 变成 **±0.8 s 全绿**。垂直立面还顺便给出了"不升空绝对过不去"的硬保证
（轮子半径 0.34 m，`slope = 7.7` 的墙爬不上去）—— 这是长沟做不到的。

**结论：调参数救不了几何。** 以后再设计飞行关，先算这条斜率。

### 被放弃的方案（如实记录）

| 方案 | 放弃原因 |
|---|---|
| 8 格深沟抛过 | 需升 11 米，窗口 0.1 s |
| 3 格沟 + 2 米台 | 窗口 0.6 s，仍太窄 |
| 9 米高塔、从塔顶起跳 | 弧顶 8–10 米，车出画面 |
| 终点离墙 4–9 格 | 弧顶比台面高 5.5–10 米；改成 `goalOff ≤ 2` 后是 +3.9 米 |
| 木箱放 `goal+2` | 三星窗口不连续（含一个孤立的 `扎@9.25–9.75`）；挪到 `goal+3` 后是连续 8 点 |

### 现在的结果

`node tools/verify.mjs` → 全绿。新增两把量尺：

- `tools/test_parts_lift.js`（34 断言，纯 Node）—— 堆叠回绕、预算按个数扣、
  `tapOnBody` 不占交互键、浮力算术、扔/扎递减、碰地自动破（**一帧最多一个**）、
  `flew_away`、终点高度门槛
- `tools/test_1_6.js`（18 断言，读真 `levels/06.json`）—— 标准解 13.5 s 三星、
  四种错误造法各自失败且**失败原因正确**、±0.5 秒抖动 9/9 通关

### 这一轮又踩到的测量教训

- `tapAt` 返回 `{kind, part}` 但没 `ok` 字段，渲染层写 `if (t && t.ok)` → 永远点不动。
  测试里我先用 `t.ok` 断言，它红了 —— **这就是量尺该有的样子**。
  修的是 `game.js` 补 `ok: true`，不是改测试。
- 「碰地自动破」第一版测试是"把车翻过来"，但翻过来的车如果净重为负会一直上飘，
  永远碰不到地，测出来是"没炸"而不是"机制坏了"。
  改成"把车按进地里 1.2 米"直接构造那个条件本身。
- 「堆叠第 4 次」我一开始断言"拒绝"，跑红了才发现实现是**回绕到 1**
  （`canPlace` 里写着为什么要回绕）。测试写的是我脑子里的实现，不是真的实现。
- **`SFX.thud` 撞名**：我给沙袋加的音效叫 `thud`，而对象字面量里**已经有一个**
  `thud(lvl)`（分级触地音）。后者覆盖前者，于是点沙袋时 `lvl` 是 `undefined` →
  时长 `0.05 + undefined*0.02` = `NaN` → `exponentialRampToValueAtTime` 抛异常。
  这是浏览器测试里 `errors:` 不为空抓到的 —— 光跑纯 Node 单测永远碰不到。
  改名 `bagDrop`，并在注释里写清为什么不能叫 `thud`。
- **托盘是 10 格不是 9 格**：`TRAY = TRAY_ORDER.concat(['eraser'])`。
  断言写成 9 直接红。测试要读 `TRAY`，不要复述零件表。

### 界面层的三处连带修复（加零件逼出来的）

加两件零件不只是"多两行数据"，它把几个**写死数量**的地方全暴露了：

| 位置 | 症状 | 修法 |
|---|---|---|
| 欢迎页「零件一览」 | 写死 7 行文案，气球/沙袋根本不在引导里 | 改成从 `RAP.TRAY_ORDER` 现推，行高/卡高跟着行数算 |
| 「零件说明」浮层 | 卡高写死 540，9 行会被挤出框底 | 高度 = 84 + 行数×58 + 46 |
| 选关页卡片 | 6 × 216 + 5 × 18 = **1386 > 1280**，卡片溢出屏幕；而点击热区用的是另一份几何拷贝 | 抽出 `levelCardsLayout()` 唯一来源，宽度按卡片数自适应，零件箱文字按可用宽度缩字号 |

顺带被测试抓到的三处**测试自身的写死**（都是"加了第 6 关/第 9 件零件"才暴露的）：
`test_ghost_buttons` 只列 5 个页签（第 6 个成了"幽灵热区"）、
`test_levelselect` 断言 `n === 5`、`test_result_keys` 把"最后一关"写死成 index 4。
三处都改成从页面读 `levels.length` / `TRAY_ORDER.length`。

### 第四处、第五处：同一句文案抄了三份

「第三颗星叫什么」这件事，原来在三个地方各写了一份手抄表：

| 位置 | 原来写的是 |
|---|---|
| 选关卡面 | `不散架（KSP）` |
| 结算页 | `不散架（KRAK SNAP）` |
| 行驶期状态条 | `不散架` |

加气球/沙袋的两颗新星时，我只改了结算页和状态条 —— 选关卡面上就会显示 **`★★★：—`**。
这不是"忘了改"，是**同一个事实存在三份拷贝**的必然结果。抽出 `challengeNameOf(lv)`
做唯一来源，并加了一条断言：三处取出来的字符串必须完全相等。

### 第六处：点气球只有数字变、屏幕上什么都不发生

`popBalloon` 改了浮力、写了 `balloon_pop` 事件，但**渲染层从来没消费过它** ——
玩家点一下气球，看到的就是"车上少了一个气球"，没有任何"啪"的瞬间。
这种缺陷靠读代码看不出来（每一层都"做了自己该做的事"），只能靠
"点了之后必须有什么东西出现在 state 里"这种断言逼出来。

补了 `spawnBurstFx`（粉色橡皮屑 + 中心白雾，粒子往**上**飘，因为气球是往上炸的），
并在 `test_lift_ui.js` 里加两条：点完气球 `state.bursts.length >= 8`，且 1.2 秒后归零
（后者防的是"粒子永久堆在 state 里"，那会让长时间试玩越来越卡）。

**这里又抓到一次我自己的"假红"**：第一次断言失败是因为 `popBalloon` 压根没调
`spawnBurst`（我只在"碰地自动破"那条路径上调了）。修的是物理层，不是测试。

### 第七处：计数器读的字段和写的字段不是同一个

```js
var before = state.car.balloonPopsBurst || 0;   // 读的是"车"上的字段（不存在）
if (popBalloon(state, balloons[bi2])) {
  state.balloonPopsBurst = before + 1;          // 写的是"局"上的字段
}
```

`car` 上从来没有 `balloonPopsBurst`，于是 `before` **永远是 0**，
`state.balloonPopsBurst` 永远被写成 1。后果：**碰地连破 6 个气球，
HUD 上一直显示"已扎 1 个"**。

发现它的方式不是读代码，是写了个"这局到底发生了什么"的探针
（`tools/probe_1_6_feel.js`），把 `pops` 和 `碰地破` 两个数一起打出来 ——
一眼看到 `pops=6（碰地破 1）`，这个式子在数学上就不成立。

修完之后补了一条纯 Node 断言：连炸 3 帧 → `balloonPopsBurst === 3`。
**"读写的对象必须是同一个"这件事，只能靠一条会红的断言来守。**

### 第八处：「我明明飞过旗子了，为什么没赢」

`Params.goalMaxAlt = 2.2` 这道门槛是必要的（否则气球流挂机就能赢，见 §5.4），
但它有一个副作用：**玩家从终点旗上空飞过去时，什么反馈都没有**。

先用 `tools/probe_over_goal.js` 量了时序，结论比预想的严重：

| 时刻 | 事件 |
|---|---|
| 9.47 s | 越过终点线，此时离地 15 米 → 不算到 |
| 12.53 s | 落回地面 → 判赢 |

也就是说**连标准解也要"飞越终点上空"整整 3.07 秒**。这 3 秒里玩家看不到任何解释。

第一版我写的是 `toast('飞太高了 —— 落回地面才算到终点')`，但那会在**每一局正常通关**
时先弹一条警告，是纯噪音。改成**随高度实时消失的读数**（`overGoalNotice()`）：
只在"此刻确实不算到"的时候显示「⚠ 还在 X 米高空 —— 落回地面才算到」，落地即消失。

这条也做成纯函数并加了三条断言（8 米高空要显示 / 1.5 米要消失 / 没到终点不提），
因为"什么时候不该显示"比"什么时候该显示"更容易写错。

### 文案和实现对不上：气球说明里写着"按按钮"

`PARTS.balloon.desc` 原文是「碰地会被扎破，也可以**按按钮**主动扎」，
但实现从一开始就是 `tapOnBody`（行驶中点车身），**根本没有那个按钮**。
零件说明是玩家唯一会认真读的地方，写着不存在的操作等于挖坑。

改成「行驶中点车身就能扎破一个；碰地也会自己破」。沙袋同理。

这类错误的共同点：**文案是在设计阶段写的，实现在后面变了，但没人回去改文案。**
它不会让任何测试变红 —— 除非有一条"说明必须提到 tapOnBody"的断言（本轮没加，
因为文案正确性很难机械判定；记在这里作为已知弱点）。

## 第 38 轮 · 失败回放一直是隐形的（量了两轮才查对）

### 症状

回放功能早就有：判负后 `state.run.replay` 里存着 20 Hz 的坐标轨迹，
`drawRun` 会按 `replayT` 逐帧重放。代码看着没问题，`errors: (none)`。
但**玩家其实一个字都看不见**。

### 第一把量尺就错了

第一版探针数"屏幕偏粉的像素"（气球是粉的），想用"有气球 vs 没气球"的差看车画没画。
结果两边只差 17 个像素 —— 差这么小，说明**车根本不是主体**。

改法是问一句"这块区域归谁"：把结算卡以外的像素单独数，
`resultT` 冻结在 0（不画卡）时全屏粉色 5283，去掉气球掉 3320 —— 车画得出来；
而 `resultT=1`（画卡）时卡外只剩 293，去掉气球只变 17。

也就是说：**卡把车盖住了。** `drawResult` 每帧画一张 760×424 的卡
（x 260..1020, y 150..574），而回放的车正好画在屏幕中央。

### 修法：不是"把卡挪开"，是"别同时画"

挪卡只是把问题推给别的分辨率。真正的错是**两套演出在抢同一块画面**。
改成串行：

```
判负 → 回放独占 2.8 s（期间不画卡、不画遮罩）
     → 2.8 s 后卡片滑入
     → 回放期间点击 / 空格 = 跳过（state.replayT = REPLAY_DUR）
```

顺带把回放本身补全：原来只画一团模糊的影子，现在重画**真的车**
（`drawPartShape` 按记录的姿态逐件画），副标题显示真实进度 `1.4 / 2.8 s`。

### 这一轮的测量教训：测试会污染被测物

要冻结回放进度，我给 `replayT` 装了个 getter + 空 setter。
于是"点击跳过"永远写不进去 —— 断言 `replayT ≈ 2.8` 一直红。
**是量尺把被测物卡死了**，不是功能坏了。改成 `delete s.replayT; s.replayT = 1.0`
（先删掉 getter 再正常赋值）才测到真东西。

顺带一条：跳过之后时间还在走，所以断言只能是 `> 2.5` 而不是 `≈ 2.8`。
写 `Math.abs(x - 2.8) < 0.01` 第一天是绿的，第二天就红了 —— 那种断言是假的。

### 结果

`tools/test_replay_parts.js`（9 断言，真浏览器 + 真 CDP 点击 + 像素对照）：
有气球的车 8259 粉像素 vs 去掉气球 2355，差 5900（阈值 400）。

## 第 39 轮 · 「没有进展」看门狗：让必输的局早点结束

### 为什么

玩家最难受的不是输，是**等了 60 秒才输**。
先量：随机造法 × 六关跑 360 局（`tools/probe_fail_duration.js`）：

| 结果 | 局数 | 占比 | 说明 |
|---|---|---|---|
| `stuck` | 317 | 88% | 平均 10.7 s 就判 |
| `win` | 22 | 6% | |
| `timeout` | 21 | 6% | **全部跑满 60.0 s** |

这 6% 是真正的问题。`tools/probe_timeout_trace.js` 跟了一局：
车以 0.2~0.4 m/s 在 1-5 的坡上慢慢溜，60 秒爬到 x=14.95（终点 25）。
**它在动**，所以 `stuck`（位移 < 0.2 m/s）永远抓不到它；
`tools/probe_timeout_role.js` 把上限抬高之后，它们最后全都变成 `stuck @ 60.1 s` ——
也就是说 60 秒上限只是个**兜底**，它没抓住病根。

### 判据要"看两条路"

最直觉的写法是"8 秒内 x 没靠近终点 2 米就判负"，但那会**误杀气球流**：
气球车横向只有 1.8~2.2 m/s，可是它一路在爬升——那是合法的推进。
所以判据是"**既**没靠近 **也**没升高"：

```js
if (gainLeft >= 2.0 || gainY >= 2.0) progLastGainT = now;
noGainFor = now - progLastGainT;
if (noGainFor >= 8.0) resolve(state, 'no_progress');
```

阈值不是拍的，是扫出来的（`tools/sweep_watchdog.js`，289 个失败样本）：

| 窗口 | 门槛 | 等效速度 | 误杀获胜 | 标准解误杀 | 抓到失败 | 平均省时 |
|---|---|---|---|---|---|---|
| 6 s | 1.5 m | 0.25 m/s | 0 | 0 | 184/289 | 8.7 s |
| **8 s** | **2.0 m** | **0.25 m/s** | **0** | **0** | **71/289** | **20.2 s** |
| 10 s | 2.0 m | 0.20 m/s | 0 | 0 | 62/289 | 9.2 s |
| 12 s | 2.0 m | 0.17 m/s | 0 | 0 | 23/289 | 0.7 s |

**不误杀的实测依据**：六关标准解的最长「无实质进展」只有 1.6 秒（1-6 升空那段），
离 8 秒有 5 倍余量。A/B 对照（`tools/probe_watchdog_ab.js`，同一批造法跑两遍）：
360 局总耗时 4603 s → 3113 s（**省 32%**），**「原本能赢却判负」0 局**。

### 这一轮最严重的坑：看门狗把两个审计全弄挂了

`verify.mjs` 跑完，**排版审计和对比度审计双双失败**，报的是
「找不到浮层标记「到达终点」——审计无效」。

两个审计造结算页的手法是一样的：

```js
s.run.result = "win"; s.run.time = 12.34; s.phase = "resolved";
```

而主循环当时只判 `state.run.phase === 'run'` 就继续推进物理 ——
`state.phase` 与 `run.phase` 已经不同步，底下的这局还在 tick。
看门狗拿着一个被外部改过的 `time`（12.34）一算 `noGainFor = 12.3 > 8`，
**当场判 `no_progress`，把刚设好的 `win` 覆盖成 `fail`**。

于是结算卡永远画不出来。查这个花了 6 个探针（`dbg_result_card` / `dbg_engine_car` /
`dbg_framerate` / `dbg_sim_speed`），因为现象很像"物理跑飞了"：
`run.time` 在 1 秒墙钟里涨到 12 秒。**其实是外部写进去的 12.34，不是物理跑飞的。**

修的是主循环：物理只在**两边都说在跑**的时候推进。

```js
if (state.run && state.phase === 'run' && state.run.phase === 'run' && !state.paused)
```

并且补了 `tools/test_resolve_sync.js`（10 断言）守**根因**：
① 状态改成 resolved 后 `run.time` 不许再涨；
② `run.result` 必须仍是 win、结算卡必须画出来；
③ 真跑一局仍然能自然结算（防止把主循环改死）。

### 教训

- **加一条"会让游戏早点失败"的规则之前，先跑一遍全部审计。**
  看门狗的语义是"时间到了就判负"，它天然会和任何"伪造状态"的测试打架。
- **同一个事实只能有一个来源。** `state.phase` 和 `run.phase` 两份状态同时存在，
  迟早会不同步；这次是测试把它撞开的，真机上（暂停/重试/回放）同样会撞开。
- 症状（`run.time` 涨到 12 秒）和病因（外部写入 + 物理没停）差了很远。
  6 个探针里有 4 个是在验证"不是物理跑飞" —— **排除法也是测量**。

### 界面层：倒计时必须提前说

`no_progress` 有一个独有的问题：**玩家完全无从得知**。`stuck` 有车停在那里的视觉证据，
`timeout` 有计时器，而"你在慢慢溜"看起来一切正常。

所以 HUD 在 `noGainFor ≥ W − 4`（还剩 4 秒）时弹一行黄色警告：
「⚠ N 秒内没有进展就要判负 —— 靠不了近、也升不高」。
文案必须同时说出**两个条件**，否则玩家会以为"我在动就行"。

失败文案也分开写：`stuck` = 「车停住了」，`no_progress` = 「一直在原地打转：
8 秒没能更靠近终点」。两条读起来必须不一样，否则玩家会觉得游戏误判。

## 第 40 轮 · 1-6 在浏览器里从来没赢过，以及"打穿了却没人说话"

### 第一件事：测试驱动器和被测引擎不是同一个东西

`tools/test_1_6.js` 一直是 18/18。它调的是 `game.js::simulate()` ——
**Node 里的另一个驱动器**，和浏览器主循环独立实现了同一套规则。

而 `probe_chapter_end.js` 用真浏览器把六关全打了一遍，1-6 的结果是：

```
[1-6] 结束状态：phase=resolved result=fail stars=0
结算卡：这一趟失败了 … 原因：卡住了：动力或重心不对
```

对照 Node：`1-6 win @ 12.53s`。**同一个关卡、同一份 SPECS，两个驱动器给出相反结论。**

病因在 `launchSpec`：它只转发了 `_presses`。

```js
// 原来
if (spec._presses) state.run.pressScript = spec._presses.map(a => ({...}));
```

`'1-6'` 的解法写在 `_drops`（4.5 s 扔 3 个沙袋）和 `_pops`（8.0 s 扎破 1 个气球）里，
这两个字段在浏览器里被**静默丢弃** —— 车全程驮着 3 个沙袋（+2.4 kg），
浮力不够、升不到 3.3 m 的平台，于是被判 `stuck`。

修法不是"给 1-6 特判"，而是让 `launchSpec` 把三种动作统一编成一条时间线：

```js
const acts = [];
(spec._presses || []).forEach(a => acts.push({ t: a.t, k: a.k || 'press', n: a.n || 1 }));
(spec._drops  || []).forEach(a => { for (let i = 0; i < (a.n||1); i++) acts.push({ t: a.t + i*0.016, k: 'drop', n: 1 }); });
(spec._pops   || []).forEach(a => { for (let i = 0; i < (a.n||1); i++) acts.push({ t: a.t + i*0.016, k: 'pop',  n: 1 }); });
acts.sort((a, b) => a.t - b.t);
state.run.actScript = acts;
```

补 `tools/test_1_6_browser.js`（16 断言）把这条**契约**钉住：先跑 Node 拿基线，
再跑真浏览器，两边必须在「结果 / x（±0.3 m）/ 时间（±0.5 s）」上一致。
实测两边都是 `win @ 12.53s, x=18.84, 扔3 扎1, 浮力 6`。

**教训**：`Node 绿 ≠ 浏览器绿`。当项目里存在两个驱动器时，
"规则正确"和"规则被送达"是两件事 —— 后者只能靠两个驱动器互相校准来证明。
`test_1_6.js` 从来不可能发现这个 bug，因为它压根不经过 `launchSpec`。

### 第二件事：18 颗星全亮，游戏一个字都没说

把六关全部跑到三星之后，屏幕上和"终局"有关的唯一表达是结算卡右下角一颗
**灰掉的**「已是最后一关」。玩家不知道自己是不是打完了、后面还有没有、这 18 颗星算不算数。

这和"第三颗星变成惩罚"是同一类错误：**内容做完了，却没有收束。**

改了三处：

1. 卡面加一句 `整章通关！` / `整章通关 · 全三星！`，下面一行只报"拿到几颗星"
   （`全章 ★ 18 / 18`），不发明新指标。
2. 那颗死按钮换成真按钮「章节总览」，键帽 `L`，点了开选关页 ——
   玩家走到终点时最想看的就是"我一共点亮了多少"。
3. 判据 `chapterDone()` 只看 `arrive`，**不看星数**：打通 ≠ 全三星。
   只通了 1-6 时它必须返回 false，此时按钮仍是灰的「已是最后一关」。

顺手改了一个文案陷阱：本关那句原来写「全部三星达成！」，
现在最后一关的卡上同一行右侧还会出现「整章通关 · 全三星」——
两句都写"全三星"会读成同一件事，所以本关那句改成「本关三星达成！」。

`tools/test_chapter_end.js`（12 断言）两头都测：**该出现时出现**，
而且**不该出现时不许出现**。后者才是这类文案最容易犯的错。
点了按钮是真的开选关页（鼠标真点 + `L` 键两条路），不是只断言标签文字。

### 教训

- **一个 UI 元素如果"点了没事发生"，它就该长得像死的，或者干脆换成有事的那个。**
  灰按钮骗人比没有按钮更差 —— 玩家会反复点它。
- **测"文案出现"要成对测"文案不出现"。** 只测前者，一个永远为真的文案也能过。
- `resultNextBtn()` 收拢了"右下角按钮是什么"的唯一来源：
  `next` / `overview` / `none` 三种。鼠标热区和键盘分支都读它 ——
  原来那里各写一遍 `state.levelIndex < levels.length - 1`，第三个分支就无处安放。

## 第 41 轮 · 结算卡上的 "+80" 是假的

### 怎么发现的

不是猜的，是量出来的。`tools/probe_coins.js` 把 1-1 连打三遍，每次都记钱包进出的差
和卡上写的数字：

```
第一遍  钱包 0 → 180（实增 180）  卡上写：+80
第二遍  钱包 180 → 180（实增 0）  卡上写：+80
第三遍  钱包 180 → 180（实增 0）  卡上写：+80
```

连打三遍之后玩家会以为自己攒了 240 块，实际 180。

### 病因：一个数字两种来源

- 卡面的是**算**出来的：`coinsOf(1, st.boxesGot)` —— 恒定返回 80。
- 钱包是**推导**出来的：`totalCoins()` ← 每关的永久星标 + 最好木箱数。

这两个在"重刷"这个场景下必然分叉。这不是"忘了更新"，而是**两个事实源**。
只要卡面还在自己算，就永远会写一个钱包没发生的数。

### 修法：量，不要算

主循环在 `saveProgress` 前后各读一次总数，把差记进 `state.coinGain`，
卡面只画这一个数：

```js
const coinsBefore = totalCoins();
const res = saveProgress(...);
state.coinGain = Math.max(0, totalCoins() - coinsBefore);
```

0 就明说「已拿满」（灰金币 + 「已拿满」），不再假装在攒钱。

### 教训

- **凡是"理论上应该是 X"的数字，都要和真实状态对一次。** 这个 bug 活了三十多轮，
  因为第一遍永远是对的 —— 只有重刷才分叉，而没人重刷过。
- 同一类错误这个项目已经犯过两次：第 36 轮是"第三颗星变成惩罚"（星是**罚**出来的），
  这一轮是"金币是**算**出来的"。共同点都是**屏幕上的数字没有连到真实状态**。
- 修完之后卡上写 `+180` 而不是 `+80` —— 因为第一遍点亮了三颗星（150）+ 一个木箱（30）。
  这才是玩家真正进账的钱。

## 第 43 轮 · 拖出网格 = 卸下（并顺手修掉了一个更隐蔽的丢件）

用户原话：**「已装备部件拖出拼装区域时直接返回待使用，从车上卸下来」。**

### 改之前量到的是什么

`tools/probe_drag_unequip.js` 用真鼠标把一个气球从格子里拖到网格左外侧松手：

```
拖动前：balloonLeft 1, cells 8
拖动后：balloonLeft 1, cells 8, stillThere true, bounce "balloon"
```

也就是**弹回原处** —— 零件自己飞回车上继续挂着。玩家把东西拖到画面外，
收到的是"它回来了"。

### 更隐蔽的那个：叠放数量在搬运途中丢掉

代码里 `state.dragMove` 是 `{ r, c, part, dir, inner }` —— **没有 `n`**，
落子时写回的也是 `{ part, dir }`。

也就是说：把一格 3 个气球拖到另一个格子，会变成 1 个，
另外 2 个静悄悄回到待使用。一次拖动**既改位置又改数量**，而且没有任何提示。
我是在读代码时怀疑的，探针 §B 证实（探针 v1 里那一节被我自己写坏了，见下）。

### 现在的语义：三种结果，因为它们真的是三件事

| 松手位置 | 结果 | 为什么 |
|---|---|---|
| 网格外（含托盘上） | **卸下**，零件回到待使用（待使用 +n） | 格子外面就是"不要它了" |
| 网格内空格 | 换格子，`n` 原样带走 | 移动 |
| 网格内被占的格子 | 弹回原处，待使用不变 | 移动**失败**，不是卸载 |

第三种是最容易写错的一条：如果把它们混成一个"放不进去就卸下"，
玩家想挪一格的路上碰到别的零件，零件就凭空从车上消失了。

### 三处配套改动（不然「卸下」是隐形的）

1. **拖到网格外时光标旁提前说「松手卸下 气球」** —— 松手是不可撤销的动作，
   出手之前必须说。这句只在光标出网格时出现，在网格内拖动时**不出现**
   （否则变成常驻噪音，测试第 7 条把守这一点）。
2. 松手后 `toast('已卸下 气球 ×3')` + 一个音高往下走的 `SFX.remove()`
   （和"放下"的音正好反向）。
3. 底部提示行加一条 `拖出网格=卸下`，欢迎引导第 3 页也加一行 ——
   这是个玩家猜不到的手势，不写出来等于藏了个操作。

"网格内被占"那条另外改成 `SFX.deny()` + `toast('那一格占着：气球 放回原处')`：
原来它也走"飞回托盘"的动画，看起来像被卸载了，而零件明明还在车上。

### 教训

- **一个手势的"取消"和"删除"必须分开。** 拖出边界既可能是"我没想好，放回去"，
  也可能是"我不要了"。默认成前者（本项目原来就是这样）会让后者永远无法表达；
  默认成后者更危险（误操作就丢件）。所以这里按**位置**分：边界外 = 删，占位 = 取消。
- **凡是搬运对象，都要问一句"它的哪些字段会被丢"。**
  `n` 就是被丢的那个。这个 bug 和"1-6 在浏览器里从来没赢过"（`launchSpec` 丢了
  `_drops`/`_pops`）是同一类：**搬运时漏了一个字段，症状却在很远的地方**。
- **断言不要写死绝对值。** `test_drag_unequip.js` 第一版写死"待使用 0 / 1 / 3"，
  满盘红 —— 因为 1-6 给了 6 个气球、基线造法只挂 3 个，待使用本来就是 3。
  改成前后差之后，测的才是"拖出这一格，待使用涨了几个"。
  写死绝对值等于把「这一关给了几个气球」这个无关事实也拖进了断言。

## 已知弱点（如实记录）

- **1-5 的 ★★ 与 ★★★ 可以一次拿全**：文档要求二者必须冲突；切片里沟只有 1 m 深，
  拿木箱的路线也能不用马达。留到 2-5《悬崖快递》用气球/伞体现冲突。
- **「不散架」这颗星在正常关卡里几乎不会失败**：五关的标准解木框都毫发无损。
  400 种随机造法里只有 1% 会撞碎 —— 也就是说这颗星现在偏"白送"。
  它需要一关**专门为它设计**（长下坡 + 落地），那是下一批气球/沙袋上线后的事。
  （第 37 轮补齐了气球/沙袋，但这一关**还没做** —— 见下条。）
- **1-6 只验证了"设计成立"，没有验证"好玩"**：18 个断言证明它可通、无解会失败、
  ±0.5 秒抖动不误杀。但"扔沙袋 → 升空 → 扎气球"这个节奏在**真人手里**是不是爽，
  必须由用户试玩判定。AI 侧只能说数值自洽。
- **飞行关的想象力受物理锁死**：轨迹斜率约 1.4:1（上升定速 2.5 / 水平 1.8），
  "飞多远"实际是"要升多高"。后续飞行关必须先算斜率再画地图。
- 网页版的"手感"只在 60fps 浏览器里成立；千星客户端是 30fps + 固定步累加，需在步骤 6 复验。
- 失败回放的节奏（0.4× × 3 s）在网页里是"重放坐标"，千星里要自己维护环形缓冲。
- 金币仍然没有消费出口（但至少卡上的数字现在是真的了 —— 见第 41 轮）。
- **`no_progress` 的阈值只在"随机造法"上扫过**：360 局里没有一局标准解被误杀，
  但真正的危险是**玩家的合理慢速解法**（比如一路慢慢蹭上坡），那不是随机造法能覆盖的。
  这条要等真人试玩才敢说安全；目前 8 s / 2 m 有 5 倍余量，是"能接受"而不是"已证明"。
- **`levels/*.json` 里的 `timeLimit: 120` 是死字段**：引擎认的是 `Params.demoTimeLimit = 60`。
  两份数字并存，迟早有人改错那一份。步骤 5 搬 Lua 时必须只留一份。
- **「整章通关」只在六关都有 `arrive` 时出现，判据不含"这一局是不是最后一关的最后一局"**。
  也就是说：玩家把 1-6 打通、之后再回去重打 1-6 时，卡上仍会写「整章通关」。
  这是有意的（意思是"这个账号打通了整章"，不是"你刚刚打通了整章"），
  但严格说它读起来像后者。要真的区分，得加一个"首次通关"的时间戳。
- **章节收束只有一句文案 + 一个按钮，没有过场、没有奖励、没有解锁提示**：
  `chapterDone()` 之后除了那句「整章通关」和「章节总览」入口，游戏没有任何新内容。
  垂直切片到这里就到头了 —— 这是切片的定义，不是遗漏。
