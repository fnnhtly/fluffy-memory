## 1. 捣蛋猪的机制骨架（从资料里抄的，不是猜的）

### 1.1 动力是"三件套"，不是"一个马达"

| 类别 | 件 | 语义 |
|---|---|---|
| **永久动力源** | 电机（绿）/ 柴油（棕）/ 涡轮（红）/ 核 | **必须放在框子里**。只提供"动力容量"，自己不产生推力 |
| **驱动工具** | 小螺旋桨 / 大螺旋桨 / 电风扇 / 黄伞 | **消耗动力容量**产生推力/升力。必须和动力源**连通**（中间要有连接件） |
| **一次性动力源** | 雪碧/可乐（短）、红/蓝火箭（长）、TNT | 点一次喷完就没了。**不需要连通**，自己就推 |
| **手动工具** | 气阀 / 黑伞 / 拳套盒 / 吸盘枪 | **完全不耗动力**，玩家按才动 |

这是"马达 + 电池"最根本区别：**动力源和推力件是两件东西，中间靠连通性耦合**。
参考里的原话："除了雀斑猪外，必须放在木框或者铁框里"、
"只要中间有动力连接件（框/可乐/火箭/分离器/弹簧都算，绳子不算），动力可以叠加"。

所以"马达"这个词在参考里**不存在**。存在的是「动力源」+「螺旋桨」。
我们现在的 `motor`（自带推力 + 自带 12 电量 + 靠电池扩容）是这两者的错误合并。

### 1.2 浮力是"一对"，不是"一个气球"

原话：

- 气球："升力小于载具的总重则会『抵消』一部分重力"、
  "碰到墙壁或地面会自动破裂，除此以外玩家也可以手动爆破气球"
- 重物（沙包）："使载具增重"、"游戏进行期间玩家可以手动卸载悬挂的重物"
- **关键布阵规则**："如果某格放置有气球，则开始游戏后，气球会被系在其下方
  最靠近自身的方框上；否则气球会直接飘走"、
  "如果某格放置了重物，则重物会系在其上方最接近自身的方框上；否则重物会直接落地"

这条"系在哪"是**布阵阶段的物理约束**，我们现在完全没有。
我们的气球是"格子里一个圆，浮力直接加到车心"，沙袋是"格子里一个袋，质量加到车心" ——
位置无关。而参考里位置决定生死：气球没系到框上就飞了。

## 2. 原神地域皮肤（用户给的方向）

用户点名了两个例子：「蒙德可以做热气球，璃月可以做仙术机关」。
按这个思路把七国各自的"技术基调"排出来，每一样都要**对应一个真实机制**，
不能只是换皮：

| 地区 | 技术基调 | 映射到哪个机制 |
|---|---|---|
| **蒙德**（风） | 风车、滑翔翼、热气球 | 浮力（气球→热气球）+ 升力面 |
| **璃月**（岩/仙术） | 机关术、归终机、仙家法宝 | **动力源**（"仙力"）+ 钟离的岩柱（结构） |
| **稻妻**（雷） | 雷楔、御影炉心 | 一次性大推力（雷楔/火箭） |
| **须弥**（草/智慧） | 虚空终端、遗迹机械 | 逻辑门/顺序控制 |
| **枫丹**（水/蒸汽） | 蒸汽机、机械齿轮 | 持续动力 + 传动 |
| **纳塔**（火） | 燃素、翼龙 | 一次性燃料 + 冲刺 |
| **至冬**（冰） | 愚人众机械、冰面 | 抓地力（冰面轮） |

### 3.2 必须落实的三条参考语义

1. **动力连通性**：驱动工具必须通过结构件连到动力源，否则不转。
   这条要能在 HUD 上看见（"这台螺旋桨没连上动力"）。
2. **气球系在框下方 / 沙袋系在框上方**：布阵阶段就校验，
   非法摆放要么禁止、要么在出发时视觉上"飘走/落地"。
3. **一次性推力烧完就没**：霄灯点一次，喷 1.2 秒，然后变成空壳。

### 3.3 不做

- 弹簧/绳子/分离器（四色）：参考里它们主要服务于"弹簧飞刀"这类 BUG 玩法，
  在 2D 单刚体模型里做不出可信行为。
- 机翼/尾翼：二维横版没有真正的气动，做了就是假物理。
- 吸盘枪：8 方向放置 + 攀爬，超出本轮。

## 6. 第 67–68 轮：托盘的边界、风的朝向

### 6.1 托盘只放本关给的零件（第 67 轮）

用户原话：「为什么本关不给的零件要显示在物品栏」。

原来 `TRAY = TRAY_ORDER + 橡皮`，十三件全画，本关不给的显示成 0 并变暗。
当时的理由是"让玩家知道游戏里还有什么"，三条都站不住：

- 1-1 只要 3 件，另外 10 件**永远**是 0，托盘大半个是死格子；
- 0 的格子仍然占位、仍然得点一下才知道没货；
- 最糟的是它把**题面**藏起来了 —— 玩家看不出这一关切给他哪几件工具，
  而那正是解谜的起点。

现在 `refreshTray()` 把 `level().partsBox` 投影成托盘，在 `startLevel` 里调用：

| 关 | 格数 | 内容 |
|---|---|---|
| 1-1 | 4 | 木框 · 木轮 · 小猪 · 橡皮 |
| 1-2 | 5 | +仙术机关 |
| 1-3 | 6 | 木框 · 木轮 · 风种 · 风车桨 · 小猪 · 橡皮 |
| 1-4 | 7 | 木框 · 木轮 · 铁轮 · 风种 · 喷气口 · 小猪 · 橡皮 |
| 1-5 | 7 | 木框 · 木轮 · 风种 · 风车桨 · 仙术机关 · 小猪 · 橡皮 |
| 1-6 | 8 | 木框 · 木轮 · 风种 · 风车桨 · 热气球 · 压舱石 · 小猪 · 橡皮 |

槽位从 46px 放大到 64px（8 格横跨 596px，左右各留 342px），
每格左上角加了 1–9 的数字键徽标 —— 键盘快捷键一直在，但界面上从没说过。

两个坑：

- `__rap` 原来是**按值**导出 `TRAY` 的，`refreshTray()` 重新赋值之后
  导出数组永远停在初始的空数组：浏览器里托盘正常，测试读到 `[]`。
  现在导出成 getter。**按值导出可变绑定 = 导出一份快照**，这类假绿最难发现。
- `test_lift_ui` 曾断言 `tray.length === TRAY_ORDER.length + 1`。它是在
  第 63 轮替换"写死 10"时写的，**看起来**跟着数据走了，但正确参照物是
  `partsBox` 而不是零件总表 —— 所以这一轮它又红了。

守卫：`tools/test_tray_scope.js`（7/7，把托盘改回全表会变 3/7）。

### 6.2 风的方向 vs 车的方向（第 68 轮）

用户原话：「为什么不把风相关的零件的箭头改成风的方向，让车受反作用力
沿风的反方向运动，为什么不给风相关的零件使用的时候给风的特效」。

箭头一直表示"**车受力**的方向"，但螺旋桨推的是**空气**，车往反方向走。
玩家看到的箭头和即将发生的事正好相反。

现在两件事分开，各自只有一个定义处：

| 函数 | 含义 | 谁读 |
|---|---|---|
| `dirVec(dir)` | 车受力方向（物理） | `step()` 的推力、力矩 |
| `blowVec(part, dir)` | 风/喷流方向（对 `blowsAir` 零件取反） | 建造期箭头、行驶期风特效 |

`PARTS` 里给 `propeller` / `jet` 加了 `blowsAir: true`；仙术机关和霄灯
是自己被推出去，不取反。物理一个数都没改：`dir` 仍然表示受力方向，
1-3 标准解仍然 x 3.5 → 16.97。

行驶期特效（`spawnWindFx` / `drawWindFx`）：
- 每个正在出力的 `blowsAir` 零件沿 `blowVec` 吐流线粒子；
- 颜色分两种：风青白、蒸汽暖橙；
- 生成点用**车体局部坐标**，随车旋转 —— 车翻过来风也跟着翻；
- 寿命 0.34 秒，停推后 0.7 秒内画面干净（实测 0 条残留）；
- 生成量按 `dt` 累积，不按帧。30fps vs 120fps 稳态 11 vs 12 条；
  改成"每帧固定 3 条"立刻变成 30 vs 120。

守卫：`tools/test_wind_direction.js`（6/6，像素级：dir=0 时格子左侧
37 个箭头色像素 vs 右侧 5 个）与 `tools/test_wind_fx.js`（9/9）。

### 6.3 一个量具把自己骗了（记下来）
`test_wind_fx` 第一版在"断电"那一步留了一行 `delete S.run.car` 的调试占位
没删。之后每一帧 `drawRun` 都在 `car.vx` 上抛异常，被顶层的 try/catch 吞掉，
画面**冻结在最后一帧** —— 于是"断电后还有 11 条粒子"看起来像产品缺陷
（特效不消失），其实是渲染循环已经死了。

这是这个项目第二次栽在同一件事上（第 57 轮是 `probe_*` 脚本读错对象）。
**量具里的调试残留会伪装成产品 bug，而且比产品 bug 更难查** ——
因为它看起来完全符合"我刚改了这块代码"的因果。

现在那一步改成真正的做法（把 `powered` 置 false），并加了一条前提断言
`B3 前提：车还在`，专门用来排除"渲染循环挂了"这种解释。

## 7. 第 69 轮：把零件焊起来

### 7.1 用户说的"各自转动"其实是什么

用户原话：「我想让车上的零件都连起来，比如两个木框的两边粘连起来，
不会在下坡时各自转动」。

先量，再改。两个探针给出了相反的答案：

| 探针 | 量到了什么 |
|---|---|
| `tools/probe_part_rotation.js` | 行驶期三块木框相对车身的 `dir` **恒为 0**；`car.a` 从 −17.41° 转到 −24.85° 时，三块木框**一起**转 |
| `tools/probe_seam_width.js` | 两块木框接缝处的木色横带 **0.451 格**宽，而单块边框只有 0.225 格 |

也就是说：**物理上本来就是刚体，没有各自转动这回事**。
但每块木框都画完整四条边，并排时 A 的右边框 + B 的左边框
并排成一道**两倍厚的墙**——眼睛把这道双倍隔断读成"两个独立的箱子贴在一起"，
车一倾斜，那道粗墙跟着转，于是更像"各自在转"。

### 7.2 修法：相邻结构件共用一面墙

`weldedEdges(hasStruct, r, c, dir)` 返回四条边各自该不该画：

- 邻居是结构件 → 这条共享边**只由一方画**，另一方跳过（不是画淡，是不画）；
- 谁画按 `(行, 列)` 字典序决定 —— 用坐标而不是遍历顺序，
  否则同一辆车在建造期和行驶期可能画出不同的缝；
- 返回值是**本地坐标系**下的四条边，因为 `drawPartShape` 里的 ctx 已经按
  `dir` 旋转过，而相邻关系是网格里的事，两者差一个 −dir·90°。

跟着一起改的还有：木纹只画外露的上下边、内壁阴影逐边、
铁角包边只在"两条相邻边都外露"的真角上画、铆钉同理。

### 7.3 数字

| 项 | 改前 | 改后 |
|---|---|---|
| 并排木框的接缝厚度 | 0.451 格 | **0.250 格** |
| 孤立木框的左边框 | 0.225 格 | 0.225 格（不变） |
| 孤立木框的右边框 | 0.225 格 | 0.225 格（不变） |

守卫 `tools/test_weld.js`（4/4）。把建造期那一侧改回 `null`（不焊接）
立刻变 3/4，读数回到 0.451 格。

### 7.4 顺手修掉的两条"假红"

改完跑全量，`test_lift_ui` 红了一条「点车身外面不误触」：`bags 2→2` 之前
出现了 `bags 0→2`。查下来是**判据在测别人的动作**：

那一局是 `launchSpec(5,'1-6')` 发的，而 1-6 的标准解带 `_drops:[{t:1.5,n:2}]`
——出发 1.5 秒后**自动**扔两个压舱石。上一段（点气球 + 等 1.2 秒看粒子散尽）
早就跑过 1.5 秒了，那次自动投掷恰好落在这个观测窗口里。

修法：先 `actScript = []` 清掉脚本动作，再用**引擎算出来的最远点**
（而不是写死"车外 220px"——那个偏移只躲开了气球，没躲开下方的沙袋）当反观点。

`test_run_banner` 也偶发过一次「2.4s 后横幅自动消失 · runBanner=0.15」，
单独重跑 6/6 —— 是无头环境里 rAF 被节流导致的计时抖动，不是产品问题。
`tools/lib/verdict.js` 自带重试，这里记一笔以免以后有人把它当成回归。

## 8. 第 70 轮：把"挂上去"的零件也焊住

第 69 轮焊的是**结构件之间**。用户那句「车上的零件都连起来」还有一半没做：
轮子、气球、沙袋、风车桨、打气筒、喷气口这些**挂在车上的**零件，
和车体之间露出一道背景，眼睛就把它当成"浮在车顶上的一件东西"。

### 8.1 判据怎么切

"连起来"不等于"任意两件相邻的零件之间都不能有背景"。气球旁边是风车桨，
两个圆东西并排，中间当然是空的 —— 那不是缺陷。真正要焊住的只有：

| 判据 | 内容 | 量具 |
|---|---|---|
| B | 悬挂件 ↔ 它下方（或上方）的结构件：接缝上必须**有一段连接件跨过** | `test_parts_connected.js` |
| C | 六关**每一关**都要满足 B | 同上（逐关现抓两帧） |

判据写成"有一段连接件跨过接缝"，不是"整条边被填满"。连接件的形态就是**一根**：
气球的绳、风车桨的立杆、轮子的轮毂 —— 它们在接缝上只占一小段。
要求整条边填满会把一个正常的气球判成"断的"。

### 8.2 修了什么

| 零件 | 原来 | 现在 |
|---|---|---|
| 风车桨 / 喷气口 | 叶片画到 h*0.78，和下方木框之间全部是背景 | 加**立杆**（0.26 格宽，中心→格子下沿）+ **底座横梁**（铺满 0.92 格） |
| 气球 | 扎口绳画到 h*0.92，差 0.04 格没顶到格子下沿 | 绳子顶到 +h，直接系在下面的木框上 |
| 打气筒 | 筒身到 h*0.14 就结束，下面 0.36 格是空的 | 加**进气管**接到格子下沿 + 底部法兰 |

六关实测（连接段占接缝的比例 / 是否居中）：

```
1-1  木框↔木轮       100%  居中   ✓
1-2  打气筒↔木框      49%  居中   ✓  （修前 0%，不居中）
1-3  风车桨↔木框      97%  居中   ✓
1-4  喷气口↔木框      82%  居中   ✓
1-5  木框↔木轮       100%  居中   ✓
1-6  气球↔木框        58%  居中   ✓
```

### 8.3 这次量具错了六次 —— 全记下来

这一轮的大部分时间不是在改画法，是在**让量具变得可信**。前五版探针
全部在行驶期做"抓两帧求差"，全部失败，而且失败方式各不相同：

1. **没等镜头收敛** → 两帧之间地形平移，差集横跨整个屏幕（1254px）。
2. **只在一列上扫** → 风车桨的叶片是放射状的，单个 x 列未必有叶片穿过，
   把叶片之间的空隙读成 0.351 格的"缝"。改画法怎么改读数都不变 ——
   因为它量的根本不是画法。
3. **用颜色枚举零件** → 漏了气球绳 `#8a6a4a`、沙袋束带 `#6b563a`，
   把零件自己画的东西算成背景。
4. **清空 `car.parts` 再抓一帧** → `drawRun` 在空零件上抛异常被顶层 try/catch
   吞掉，画面**停在上一帧** → "空场景"和"整台车"几乎一样，
   差集只剩镜头抖动，零件中心一个都不在掩码里。这一条最阴：
   它看起来像"全都是缝"，其实是渲染循环已经死了。
5. **探针点取格子中心** → 木框是**中空**的，中心天然是背景，
   于是报了 2/8 件"不可见"。改成九点采样才修好。
6. **`R.SPECS['1-4']` 不存在** → 那两关各有两种解法，key 是
   `1-4i`/`1-4w`、`1-5n`/`1-5m`。取到 undefined，`Object.keys(undefined)`
   抛异常被吞掉，于是那两关在报告里变成"无悬挂对" —— 而"无悬挂对"是
   **合法**的（1-1 真的没有），两关一个零件都没量却看起来像通过。

最后一条不再靠"我觉得够了"，而是加了一条显式断言
`A3 前提：六关每一关都真的装上并扫过了`，缺一关立刻红。

### 8.4 判据 B 被删掉了

`test_parts_connected.js` 一开始有一条"结构件之间的接缝不漏背景"的断言。
它永远 100% —— 把木框的左右边框整段删掉，它**仍然 100%**。
原因：相邻两格的公共格线上必定有一条外描边压在格线上，
焊接之后是共用的一条，没焊接时是两条。所以它量的不是"焊没焊"。

一个删掉被测代码还不红的判据，不能留在测试里充数。
"两个木框的两边粘连起来"这件事由 `tools/test_weld.js` 负责 ——
它量的是**接缝那条墙有多厚**（0.451 → 0.250 格），把焊接关掉就变红。
`test_parts_connected.js` 只保留它量不到的那一半。

## 9. 第 71 轮：删掉动力容量，换成三颗种子

用户原话：「不要设置什么动力容量的设定，让风种子可以一次性生成一个范围风场
让携带伞/风之翼的车向上飞，让岩种子可以一次性从脚底升成一个范围性的岩柱
让车抬升，雷种子可以让车进入一种状态，让车在一定时间内快速冲刺并且可以穿过
雷屏障」

### 9.1 删掉的是什么

"动力容量"整套：`powerSrc` / `drawPower` / `powerGrid` / `powerSupply` /
`powerDemand` / `powerShort` / `powerSpare` / 超载打折 / "必须紧贴框才通电"。

它有三个毛病：
1. **要先算除法**。玩家开局的工作是心算 2+5 对比 1+2，而不是造车；
2. 它让"装得下几个桨"变成唯一的设计维度，零件本身的差别被压平；
3. 用户明确说不要。

现在驱动件**装了就一直转**。推力全部来自零件表里的 `thrust`。

⚠ 删一个系统最麻烦的地方不是删代码，是**删掉所有还在读它的地方**。
这一轮因此红了六处，每一处都是"读一个已经不存在的字段"：

| 位置 | 症状 | 为什么难发现 |
|---|---|---|
| `drawHud` 的 `pSup` | **每帧** `ReferenceError`，整个 HUD 画不出来 | 异常被 `frame()` 的 try/catch 吞掉并画成红条，而测试读 `console.error` 时用了 `a.value`（Error 对象只有 `.description`）→ `errors:` 后面一串空白，看起来像"没有异常" |
| `spawnWindFx` 的 `p.powered` | 所有风特效都不生成 | `undefined` 恒假，画法本身没坏，`test_wind_fx` A 组三条全红 |
| `failCulprit` | 每一局失败卡都弹「动力不够（装 undefined 点）」 | 只有失败局才走这条路 |
| 结算卡/建造面板的 `powerSupply` | 显示 `NaN` | 只在特定面板 |
| `challengeStatus` 的 `powerSpare` | 两条 fixture 都判"满足" | 分支读 `state.seedUse`，旧 fixture 塞 `car.powerSupply` → 恒 undefined → `0 === 0` |
| `audit_parts_spec` 的 `html` 变量 | 整个审计脚本 `ReferenceError` | verify 报「无法解析」，**一条断言都没跑到**，看起来像审计挂了 |

教训：**删一个字段之后要搜的不是定义，是读它的地方**。
`tools/audit_state_fields.js` 的 A 组（"引擎赋过值、渲染层没出现过"）
和 B 组（"渲染层读了个空"）本来就是为了抓这类错误，这一轮它们没有覆盖
`powerSupply`，因为它两边都出现过 —— 一个字段在两边都出现**不等于**它有值。

### 9.2 三颗种子

| 种子 | 效果 | 参数 | 一次性的意义 |
|---|---|---|---|
| 风种 | 脚下生成半径 6 米、寿命 3 秒的风场 | `windRadius/windTtl/windRise` | 时机是玩法：风场只在那里 3 秒 |
| 岩种 | 脚下升起 3 米宽、3 米高的岩柱 | `pillarW/pillarH` | 用完就没了，站上去就不能再升 |
| 雷种 | 4 秒冲刺（能穿过雷屏障） | `dashTime/dashAccel/dashMaxSpeed` | 4 秒里必须过墙 |

配套新增两个**吃风件**：伞（系数 1.0）、风之翼（系数 1.8）。
它们只在风场里有意义，平时是纯负重 —— 这就是这个机制要的取舍。

**风场只对吃风件做功**，这一条是整套机制的核心：
第一版写成"风场无条件抬升整台车"，于是风种变成免费的上升按钮，
伞和风之翼没有存在理由。`test_seeds.js` 的 B6 就是这条的反向对照
（没带伞的车在同一个风场里必须不动），实测把条件去掉它立刻红：
"升高 2.43 米"。

风力的写法也踩过一次：直接 `fy += windRise × 质量` 只够对抗 2.0，
而重力是 16 —— 车纹丝不动（B8 量到 +0.00 米）。必须
`fy += (G + windRise × 系数) × 质量`，`windRise` 才有"净上升加速度"
这个直觉含义。

### 9.3 岩柱改的是 `groundY`

`triggerSeed('geo')` 不改车的速度，它往 `state.pillars` 里塞一根柱子，
然后**所有读到"地面"的地方**都改走 `groundY(state, x)`：
车轮、车壳四角、气球碰地、掉落的碎片、木箱高度、终点高度判定。

这是这一轮最容易出错的地方：少改一处就会出现"车被柱子托住了，
但终点判定还按原地形算"这种自相矛盾。六处全部收进一个函数，
而且**柱子的范围之外返回原地形** —— "范围性"就是这一条。

### 9.4 雷屏障是"推回去"，不是"判失败"

挡住的方式是 `car.x` 推回屏障前 0.02 米 + 抹掉 vx，不是 `resolve(fail)`。
玩家撞上墙的第一反应应该是"我被挡住了"，不是"游戏结束了"。

### 9.5 量具这一轮改了七次

`test_seed_fx.js` 验的是"玩家能不能看见"（引擎断言在 `test_seeds.js`）。
它几乎整轮都在修自己：

1. **颜色辨识**（青色/暖砂/紫色占比）→ 全部读 0%。三个效果都是**半透明**的，
   叠在洞穴深青背景上出来是 rgb(62,100,91)，既不"青"也不"亮"。
2. 改成**区域差分**，但采样区在**车身上** → 差异里混进"车被托起来了"。
   反向验证抓到的：把绘制整个删掉，断言照样通过。
3. 改用 `state.camLive` 反算坐标 → 它带着**震屏抖动**，采到旁边的草地。
   改成 `state.camLastDraw`（这一帧真正用的镜头）。
4. 采样区换成"车旁 4.2 米" → 但车上有**风车桨**，它每帧吐 14 条流线，
   68% 的差异全是那些粒子。改成不装桨。
5. 岩柱采样区挨着车 → 柱子抬高 groundY → 车被托起 → 差异还是"车动了"。
   最终改成**不触发岩种，直接往离车 8 米处塞一根柱子**：
   这一支只回答"画没画出来"，"车被托高了吗"归 `test_seeds.js` 的 C4。
6. 镜头 zoom 指数收敛，触发后**一直**朝新目标爬 → 加了 `state.__lockCam`
   （渲染层读它来跳过缓动和震屏）。改 `camState` 是不行的：
   下一帧就被缓动覆盖 —— 这个项目反复踩的同一类坑。
7. 采样区尺寸用 `min(cv.width, cx+half)` 夹 → 靠边时两次采样尺寸不同，
   `diffPct` 返回 `-1`，差异显示成 **"-1%"**。
   改成先夹起点，尺寸恒为 `2*half`。

七次里**五次是反向验证抓到的**（把绘制删掉，断言仍然通过）。
这条方法本身值得记下来：**判据写完不算完，要把它该保护的代码删掉，
看它会不会红**。不红就说明它量的是别的东西。

## 10. 第 72 轮：让三颗种子各自有一关

第 71 轮把机制做出来了，但**只有风种出现在任何一个关卡的零件箱里**。
岩种和雷种是"能从零件表调出来、但没有任何一关会给你"的状态 ——
玩家永远见不到它们。一套机制做出来了却没有内容用它，等于没做。

### 10.1 新增两关内容

| 关 | 机制 | 形态 |
|---|---|---|
| 1-5（改） | 雷种 | 路线中段一道雷屏障（col 20，4 米高）。不带雷种 → 被顶住；带雷种按 F → 冲过去 |
| 1-7（新） | 岩种 | 一道 2 米高的硬台阶。爬不上去；岩种在车脚下升起 3 米柱子把它顶上去 |

两关都验了**三个方向**（`tools/test_seed_levels.js` 24/24）：
带种子能过 / 拆掉种子过不去 / **带着种子但不按**也过不去。
第三条最重要 —— 它是玩家最常见的失败姿态。

### 10.2 这一轮修掉的三个真实引擎缺陷

这三个都是"关卡做不出来"逼出来的，不是测试写错：

**① 柱顶会踩空 → 加顶盖（`pillarCap`）**
柱顶是 3 米高的平台，但左右两侧立刻回到原地形。车一往前挪就踩空翻滚
（实测 0.25 秒内翻到 −52°，最后卡死在 −143°）。
现在柱身之外还延伸 2 米"顶盖"，车能往前开出去再落地。

**② 柱子升起把车弹飞 → 柱顶**逐渐长高**（`pillarRise`）**
第一版让 `groundY` 立刻返回最终柱顶。后果：柱子升起那一帧，
车的穿透量从 0 跳到 3 米，法向力 `N = 320·pen` 顶到上限，车被弹飞。
现在柱顶在 0.35 秒内从地面线性长到全高 —— 车是被**上升的地面**顶上去的，
每帧穿透只有几厘米，弹簧力是正常的接触力。
这也让画面上那条"缓缓升起"的柱子变成**物理**而不是装饰。

**③ 车轮在柱顶上按原地形的坡度滑 → `groundSlope`**
这是最容易漏的半件事：`groundY` 已经让车轮的**高度**用柱顶，
但法线/切线仍然读 `ter.surfaceSlope(x)` —— 那是**地形**的坡度。
于是在柱顶那块平地上，车感受到的仍然是柱下地形的倾角，
实测从 +8.5 m/s 一路滑到 −4.9，最后卡死在柱顶边缘。
柱顶是平的，坡度就该是 0。

**后果对比**：修 ③ 之后，"岩柱关"这个设计从 1944 组搜索里只有 2 组能过，
变成 744 组能过；触发窗口从 0.2 秒变成 2.0 秒。
也就是说**前两个修的是一个手感问题，第三个修的是"这个机制根本不能用"**。

### 10.3 关卡形状被"正确打法不该掉耐久"约束

1-7 最初设计成**坑**（掉进去爬不出来）。它在机制上完全成立，
但坑的入口落差让车以 7 m/s 砸到底 —— 一次 `struct_hurt`，
掉一点耐久。而 `tools/test_touch_ladder.js` 有一条
「标准解 0 次掉耐久」，它是**对的**：正确打法不该被误伤。

所以关卡换成 2 米**台阶**：车是"被顶上去了"，不是"掉下去了"，
全程零撞击。判据没有为关卡让路，是关卡为判据让路。

### 10.4 加了第 7 关，红了一片 —— 全是"写死 6"

这一轮最花时间的不是做机制，是**所有把"六关"写死的地方**：

| 位置 | 症状 |
|---|---|
| `test_level_thumbs` 的 `CW=216, GAP=18` | 关数一变卡片宽度从 216 掉到 158，测试还在按旧几何采点 → 采到卡片外的背景，1-1/1-7 都读出纯黑 |
| `test_chapter_end` 的最后一关写死 `1-6` | 1-6 现在**确实**有下一关，「已是最后一关」当然不该出现 |
| `test_time_limit` 的 `['1-1',...,'1-6'][i]` | 第 7 关拿到 `undefined`，`applySpec` 抛异常 |
| `test_touch_ladder` 的 `KEYS[i]` | 同上 |
| `audit_level_fields` 的 `EXPECTED` | 新字段 `barriers` 被当成死字段 |
| `test_stars` 的「满星 1 / 6 关」 | 断言文案里写死了总关数 |

不写死关数、不按下标对齐。

其中 `test_level_thumbs` 的修法值得单独说：不是"把 216 改成 158"，
而是**问渲染层要 `levelCardRect(i)`** —— 那本来就是渲染层自己用的函数。
改数字只能撑到下一次加关，读同一个来源才不会再犯。

### 10.5 还有一处"两条路径只改了一条"

`_seeds` 在 Node 的 `simulate` 里第 71 轮就支持了，但浏览器的
`launchSpec` 没有 → 1-5e / 1-7 的标准解在 Node 里能过、**真浏览器里
一次都没验证过**。`test_all_levels`（真浏览器跑每一关）就是因此红的。

这类漏洞 Node 测试永远抓不到，因为 Node 走的是另一条分支。
只有真跑一遍浏览器才看得见 —— 这也是"每一步都必须有真实浏览器证据"
这条规矩最实在的一次回报。

## 11. 第 73 轮：风种补上它自己的一关（1-8）

第 72 轮说"三颗种子各自有一关"，但严格讲只做到了两颗：

- 1-5 → 雷种（必须用）
- 1-7 → 岩种（必须用）
- 1-3 → **发了**风种，但那关的第三星是「一颗种子都不用」

也就是说风种在 1-3 里是**诱饵**，从设计上就不该被用。
三颗种子里只有它没有一关"必须用它"。这一轮补上 1-8「乘风而上」。

### 11.1 为什么是"缓坡"不是"墙"也不是"沟"

先试了两种形状，都不成立：

**深沟**：宽 5~10 米、深 2~8 米、有无螺旋桨，十几组全过不去。
原因是算得出来的：风场的抬升是**垂直**的，水平速度只有螺旋桨给的
5 m/s²，飞过 6 米需要 3 秒以上，而风场只活 3 秒。
"风口跨沟"这个动作在这组参数下物理上不成立。

**直墙**：能过，但**触发窗口只有 0.25 秒**（t=3.5 恰好）。
再细扫发现所有能过的组合都会撞出 `lvl4 / struct_hurt` ——
车被风举起来、贴到墙面上、卡一下才翻上去。
而"标准解不该掉耐久"是 `test_touch_ladder` 里一条**对的**判据。

**缓坡**（最终方案）：col 24 起 6 格升 4 米。
车被风托着沿坡往上，全程零撞击。实测：

```
标准解 (t=3.0)  → win ★★★  hurt=0  big=0
不用风种        → fail stuck  x=23.6（卡在坡脚）
拆掉伞          → fail stuck（风场托不动）
```

触发窗口 t=3.0~3.75（0.75 秒）—— 比墙方案的 0.25 秒宽 3 倍，
而且**无伤**。判据再一次没有为关卡让路。

### 11.2 顺手把"关 → 标准解 key"抽成一份

第 72 轮加第 7 关时，**8 个脚本各写了一张自己的表**（或更糟：
按下标取 `['1-1',...,'1-6'][i]`），加一关红了 8 处，每处修法都不同。
所以加第 8 关之前先把表抽成 `tools/lib/specmap.js`：

- Node 侧：`require('./lib/specmap.js').specKeyOf(levelId)`
- 浏览器侧：页面导出 `window.__rap.SPEC_OF`（同一份数据的副本）

`specKeyOf` 找不到时**抛出**而不是返回 `undefined` ——
返回 undefined 的后果是调用方拿到 `SPECS[undefined]`，
然后在 `applySpec` 里抛一个和真实原因完全无关的 TypeError。

这次加第 8 关，红的地方从 8 处降到 3 处，而且都是**真问题**：

| 位置 | 真问题 |
|---|---|
| `test_progress_watchdog` | `window.__rap.SPEC_OF` 根本不存在 → `.map` 抛 TypeError。**这条断言在这之前从来没被真正执行过** —— `keys[i] \|\| lv.levelId` 的兜底让 1-1~1-7 全部"碰巧"对上（关卡名和 key 恰好相同），直到第 8 关才露出来 |
| `test_chapter_end` | 最后一关写死 `'1-7'`；`others` 表手写 7 项漏了第 8 关 |
| `test_level_thumbs` | 1-8 借了 `field`，和 1-1 撞色（差 16 < 18） |

第二条尤其值得记：`others` 漏一项 → "全通"这个前提建不起来 →
后面**四条**断言跟着全红。一条前提断言写错，会伪装成四个产品缺陷。

### 11.3 新增第三套配色 `windy`

1-8 一开始借 `field`，和 1-1 的缩略图平均色差只有 16（阈值 18）。
新增 `windy`（青绿，rock `[96,150,150]`），和现有七套的两两最小色差 58。
这也顺手验证了第 72 轮那条修法是对的：判据没改，只是补了一套配色。

## 12. 第 74 轮：种子在手机上点不出来

### 12.1 问题比"少一个按钮"严重得多

做完 1-8 之后我查了一遍三颗种子的兑付路径，发现：

- 唯一触发方式是 **F 键**。全项目只有 `if (k === 'f')` 一处；
- 没有任何 `btnRect('seed')`，没有触屏入口；
- 整个文件里 `touchstart` / `pointerdown` **一次都没出现**。

而 1-5 / 1-7 / 1-8 的**解法只有种子**（第 72–73 轮刚证明过：
不用种子必过不去）。所以结论是：**这三关在手机上根本过不去**。
而用户在第 64 轮明确要求「长按屏幕出摇杆控制（电脑，手机）」——
这个游戏本来就是打算给手机玩的。

这也是引导问题：HUD 上从来没出现过 F 这个键，唯一提到它的地方是
**失败之后**的诊断语。玩家要先输一次才知道有这么个操作。

### 12.2 按钮的三态

| 状态 | 表现 |
|---|---|
| 还有种子 | 亮底 + 种子图标（和托盘里同一个形状）+ 左上角 `F` 键帽 + 剩几颗 |
| 已用光 | 灰底 + "已用"，还能看见但点不动 |
| 车上没种子 | **不画**，`btnRect('seed')` 返回 `null` |

第三态是关键：幽灵热区是这个项目反复踩的坑（`test_ghost_buttons` 把守）。
热区和绘制共用同一个判据 `seedInfoOf(run).left > 0`，不是各写一遍。

点击走 `RAP.triggerSeed(state.run, info.next)` —— 和 F 键**完全相同**的入口，
不是另写一份逻辑。一次性/范围性/音效全在那一个函数里。

### 12.3 这一组的第五个判据是必需的

`test_seed_button.js` 有 17 条断言，分五组：

| 组 | 证明 |
|---|---|
| A | 按钮存在、在画面内、够大、不压交互键 / 暂停 / 重开 / 帮助 |
| B | 点它真的触发风场，参数和键盘触发一致 |
| C | 车上没种子时**没有热区**，点那片空白不会凭空放出风场 |
| D | 用完之后点不动（一次性） |
| E | **按钮真的被画出来了**（区域像素差分） |

E 组是必需的：A~D 全都能在一个"什么都不画"的实现上通过 ——
只要 `btnRect` 返回矩形、点击分派在那里。

而 E 组第一版**恒绿**：把绘制整块删掉仍然 16/16。原因又是那两条：
摘掉种子会改车重 → 落点变 → 镜头跟着动；`triggerSeed` 里有 `shake = 0.5`。
修法和 `test_seed_fx.js` 一样：**锁镜头**（`state.__lockCam`，它顺带把 shake 归零），
再加一条 `E0 锁镜头后同状态两帧自身差异 < 1%` 的自证。

三处反向验证（`tools/_redproof_seedbtn.js`）：

```
去掉热区    → 4/8    （A1/B0b/E1/E2 红）
去掉绘制    → 15/17  （E1/E2 红）
去掉点击分派 → 15/17  （B1/B2 红）
```

反向验证脚本自己也踩了一次坑：文件是 CRLF，而锚点用 `\n` 拼的，
三个用例里两个报"找不到"。**反向验证脚本自己也要能失败得清楚** ——
报"找不到锚点"和报"判据不红"是两件完全不同的事，混在一起会让人
去修错的东西。现在它先归一化行尾、再匹配、并把"找不到"和"仍然全绿"分开报。

## 13. 第 75 轮：测试自己把磁盘写满了

### 13.1 症状

`git commit` 报 `ENOSPC: no space left on device`。查下来：

```
%TEMP% 下 1362 个 edge* 目录，占 27.8 GB
```

每一个是某次测试启动 headless Edge 时 `--user-data-dir=` 指定的配置目录。
脚本跑完**从来没有删过**。全项目 150 个脚本各自 spawn 浏览器、
各自拼一个 `path.join(os.tmpdir(), 'edgeXXX-' + Date.now())`。

这不是"某个脚本写错了"，是**收尾逻辑从来没有存在过**。

### 13.2 为什么修在 `killTree` 上

150 个地方各加一行清理必然漏掉几个 —— 第 72 轮已经证明过这种扩散的代价
（加一关红了 8 处，每处修法都不同）。而 `killTree()` 是每个脚本**唯一**
都会走的收尾口（`A.finish` 调它，`asserts.js` 导它）。

所以：`killTree` 杀完进程之后，把 `child.spawnargs` 里的
`--user-data-dir` 也删掉。判定和删除读**同一份** `profileDirOf()`。

### 13.3 删一次的实测结果：一个都没删掉

第一版写完，跑了一次真测试，`%TEMP%` 里的目录**一个都没少**（还多一个）。
用 `probe_edge_orphan.js` 分开量三件事，拿到答案：

```
1) 起来之后，带这个 profile 的进程：15 个
   已执行 taskkill /PID <launcher> /T /F
2) taskkill 之后还剩：0 个              ← taskkill 其实是有效的
3) 此时目录删得掉吗：false（EBUSY）      ← 但文件还没释放
4) 等 1 秒之后：true                    ← 只是需要时间
```

也就是说 `taskkill /T /F` **返回**时，浏览器进程只是收到了终止信号，
它手里的 sqlite / leveldb 文件还没关。紧接着 `rmSync` 必然 EBUSY。
第二版重试 3 次 × 120 ms —— 仍然不够（实测要 ~250 ms，而 3×120 的
三次尝试都挤在文件释放之前）。

最终：**最多等 1.5 秒，一旦目录消失就立刻退出**。正常情况约 250 ms。
第三版之后，连续跑三个真测试，`%TEMP%` 里 `edge*` 从 0 → 0。

### 13.4 两道防线，不是一道

只改 `killTree` 有一个风险：**以后新加的脚本可能不走它**。所以再加两道：

| 守卫 | 证什么 |
|---|---|
| `test_temp_hygiene.js`（6 条） | `killTree` 真的会删；没有该参数时不报错；删不掉时不抛异常；`RAP_KEEP_PROFILE=1` 时保留；清扫器只认自己的目录形状 |
| `audit_profile_leaks.js` | verify 里**每一个** spawn 浏览器的脚本都会经过 `killTree`（当前 66/66） |

第二条是**元层**的：它不测游戏，它测"跑测试这件事本身会不会把机器搞坏"。
这类守卫以前一条都没有 —— 所以 1362 个目录堆了整整一个项目周期才被发现。

### 13.5 清扫器只认形状

`looksLikeProfileDir(name)` 只认 `edge<字母数字前缀>-<13 位毫秒>`：
不认 `edge`、不认 `edge-cases`、不认 `node-compile-cache`。
一个误删别人临时目录的清扫器比不清理更坏。

测试自己也踩了一次：第一版夹具造了 `edgeProbe-a-<ts>-<rand>`
（两个破折号 + 尾部随机数），清理器正确地**拒绝**了它 ——
**测试的夹具必须和产品同形**，否则它验的是自己造的一个不存在的东西。

还有一个一次性的手动入口 `tools/clean_temp_profiles.js`（默认只统计，
加 `--apply` 才删），用来回收"上一次跑崩/被 Ctrl-C 打断"留下的孤儿。

## 14. 第 76 轮：零件各自旋转，是因为一个符号

### 14.1 用户看到了什么

> 木框不要这样少一边，零件不要各自旋转

截图上：车停在斜坡上，三块并排木框**每一块都像缺了一条边**，
而且三块**各自歪着**，看不出是一辆车。第 69 轮的焊接（共享墙只画一次）
本来是专门修这个的，`test_weld` 也一直是绿的。

### 14.2 根因：一个符号 + canvas 的 Y 轴朝下

```js
// 修之前
const baseRot = p.def.wheel ? 0 : ((p.dir || 0) + (car.a * 180 / Math.PI) / 90);
```

- 世界坐标 **Y 向上**，`car.a` 逆时针为正；
- canvas **Y 向下**，`ctx.rotate(θ)` 顺时针为正。

所以要让零件跟着车身转 `a`，必须传 **−a**。传 +a 的后果是每件零件
**相对车身多转了 2a**：斜坡 20° 就是 40°。

40° 的偏转意味着每块框的竖边被转到格子外面去了 ——
焊缝对不上、木色边跑到格子外，"少一边"和"各自旋转"是同一个 bug 的两种说法。

**第三处**：轮子当时是 `baseRot = 0`（**完全不跟车身转**）。
那是第三种朝向：车架歪 40°、轮子保持水平。轮子是装在车架上的，
必须和车架同角；它自己的自转是 `spin`，在 `drawPartShape` 里单独叠加。

修完之后三个朝向合一：

```js
const baseRot = (p.dir || 0) - (car.a * 180 / Math.PI) / 90;
```

### 14.3 为什么以前的测试全是绿的

`test_weld` 和 `test_parts_connected` **只在建造期**量接缝 ——
而建造期 `car.a` 恒为 0，那个符号根本不起作用。
行驶期的形状从来没有被量过。这是"量具只在一种输入下验证过"的典型：
公式里有一个变量，测试只把那个变量钉在 0。

### 14.4 两条新判据

**`test_rigid_parts.js`（7 条）** —— 整车必须是刚体：
在**车身局部坐标系**里，任何倾角下画出来的形状都必须一样。
做法是「车 vs 背景」差集取掩码，在局部网格上比对。

| 倾角 | 与 0° 的形状一致率 |
|---|---|
| 20° | 97.7% |
| −20° | 96.5% |
| 45° | 95.7% |

修之前是 84.3% / 80.7% / 86.1%。

C 组是必需的：轮廓比对对**圆形的轮子**不敏感 —— 反向验证时把轮子改回
`baseRot = 0`，A 组仍然 7/7（剪影几乎不变）。所以 C 组直接钩
`ctx.translate`/`ctx.rotate` 问渲染层"这一帧每件零件拿到多少角度"：

```
C1 没有零件保持直立（不出现 0）   → 轮子不跟车转会被抓到 16 次
C2 没有零件转了 +a（符号没反）
C3 零件确实转了 −a
```

**`test_frame_edges.js`（7 条）** —— 焊接的缝在行驶期还在不在：

```
倾角 0°   竖缝 [1, 1, 1, 1]  长边 [1, 1]
倾角 20°  竖缝 [1, 1, 1, 1]  长边 [1, 1]
倾角 −20° 竖缝 [1, 1, 1, 1]  长边 [1, 1]
```

把符号改回去：`[0.61, 0.65, 0.66, 0.57]` —— 缝掉了四成，正是用户看到的。

### 14.5 这一轮踩的坑（都记在工具的头注释里）

1. **两次 `getImageData` 在同一次 JS 执行里** → 中间没渲染，差集恒为空
   （第一次量到"车体像素 0"）。拆成两次 evaluate + sleep。
2. **采样点算错半格** → 量到空气，读数全 0。先把每格的世界/屏幕坐标打出来核对。

   `undefined`，`JSON.parse` 报「"undefined" is not valid JSON」——
   那句红完全不指向真因（真因是 `Identifier 'v' has already been declared`）。
   现在 `ev` 检查 `exceptionDetails` 并原样抛出。
4. **测试假设了上一段留下的状态** → C 组沿用 A 组最后的 45°，钩到 −0.7854
   而期望 −0.349，C3 红得"有道理但没用"。测试必须自己摆状态。
5. **容忍度必须被反向验证** → 95% 这个门槛是先有数据再定的，

## 15. 第 77 轮：车在下坡前就歪了（质心假装在原点）

### 15.1 症状

> 车在下坡前会异常倾斜甚至翻倒

在**纯平地**上从 0° 松手，1-1 的标准解会自己歪到 **−4.8°** 并停在那里；
两格的小车更狠：平地直接翻到 **−134.9°**（底朝天）。
斜坡上则表现为"车身比坡度多歪 11°"。

### 15.2 根因：三处「质心假装在原点」

1. **重力只有力、没有力矩。** `fy = −G·m`，`tq` 里没有它 ——
   等于宣称整车质量集中在局部原点。而 1-1 标准解的真实质心在 **lx = −0.5**。
2. **轮子法向力的力矩按"绕原点"算，还乘了一个 0.5。**
   实测：两轮 N 相等时绕原点的力矩是 −50.2，折半 −25.1，
   而缺失的重力力矩恰好是 **+50.4**。那个 0.5 是**补偿**，不是物理。
3. **弹簧接触模型本身分不出不均的 N。** 这一步是第 77 轮最关键的发现：

> 弹簧接触里 `N ∝ 穿透量`。平地上两个半径相同的轮子刚性固定在同一个车身上，
> 穿透量必然相等 → N 相等 → 绕质心的力矩 = N·(x₁−x_com) + N·(x₂−x_com) ≠ 0
> （只要质心不在轮距中点）。于是车身**必须**歪到两轮穿透量不同，
> 才能凑出一组能平衡的 N。质心偏 0.147 m 就要歪 15.6°，再歪下去就翻。

真实的刚体静力学不是这样：两个接触点是**静不定**的，N 由平衡方程分配，
与穿透量无关。所以改成「弹簧只决定**总**法向力，两个轮子之间按杠杆分配」：

- 自重那部分（`min(弹簧总量, 自重分量)`）按**杠杆定则**分 → 静止时净力矩 0；
- 超出自重的部分（落地冲击）仍按**穿透量**分 → 保留"撞台阶会抬头"的手感。

两者连续过渡，没有开关、没有阈值跳变。

### 15.3 一个错误的判据与一个正确的判据

`test_car_stance.js`（13 条）是这一轮的主要量具。它有两条判据在写的过程中
被**自己**推翻了：

- E 组第一版写"整趟里任何时刻 |a − slope| ≤ 8°"，实测最大 11.2°。
  查下来 t=4.37 时车已经越过坡底拐点、**前轮离地、整台车在飞** ——
  那时坡度对姿态没有约束力，惯性才是。判据改成"两轮着地且慢于 2 m/s"。
- 另一条更值得记：**质心偏 0.147 m 就要歪 15.6°** 这个数字是被
  "关掉杠杆分配"的反向验证逼出来的。没有那一步，我会以为
  加个重力力矩就够了。

### 15.4 顺带暴露的两个真问题

质心修正让物理变对了，于是**两条一直绿的测试红了**，而且都是产品问题：

| 测试 | 症状 | 真因 |
|---|---|---|
| `test_parts_lift` | "落回地面才算到达" FAIL | 夹具把车放在 `x == goal.col`，修完之后车在第一帧被推回 0.0002 米，`>=` 差一点点。夹具压线太死 |
| `test_touch_ladder` | 1-7 / 1-8 标准解掉耐久 | 见 §16.3 |

## 16. 第 78 轮：删掉焊接边

### 16.1 用户要求

> 把这个缺边的机制删了，车在下坡前会异常倾斜甚至翻倒

第 77 轮已经证明了"各自旋转"的根因（`car.a` 符号），修完之后缝是对齐的。
但"**缺边**"这个观感还在 —— 因为它就是焊接本身：相邻结构件共用一面墙，
每块框只画朝向外部的那几条边。用户看到的是"每块都缺一条边"。

### 16.2 删掉的是什么

一整套，不是一处开关：

| 删掉的 | 处数 |
|---|---|
| `WELD_GRID` / `WELD_NAMES` / `weldedEdges()` | 1 个函数 + 2 个常量 |
| `buildHasStruct` / `runHasStruct` | 2 个函数（查邻居的入口） |
| `drawPartShape` 的第 9 个参数 `edges` | 1 个签名 + 全部 `if (E.xxx)` 分支 |
| 调用点 | 建造期 1 处 + 行驶期 1 处 |

`test_weld.js` 的判据**整体反转**（而不是删掉测试）：
原来守"接缝只有一块边框厚（≤0.30 格）"，现在守"接缝是两层（≥0.35 格）"。

> ⚠ 这不是"把判据放宽到能过"。这是**需求变了**：用户用一个观感问题
> （斜坡上像缺边）换掉了另一个（并排像两个箱子）。判据跟着需求走，
> 而不是跟着当前实现走 —— 这一点写在文件头，免得下次有人以为是回归。
> 而且它仍然会失败：把焊接加回来，接缝掉回 0.22 格，断言立刻红。

新增 `test_no_welding.js`（11 条）守"真的没了"：名字一个都不剩、
`drawPartShape` 只剩 8 个参数、每块框四条边木色覆盖率都 ≥ 0.6、
接缝确实是两层。

### 16.3 物理修好之后，两关的设计问题暴露了

`test_touch_ladder` 有一条**对**的判据：「标准解不该掉耐久」。
它一直是绿的，而第 77 轮修完质心之后立刻红了 —— 1-7 和 1-8 各掉一点耐久。

查下来不是判据变严了，是**以前靠错误的物理在撑着**：

- **1-7**：车以 5.9 m/s 撞上 2 米台阶的立面。旧模型把撞击力矩折半，
  所以"撞了但不掉耐久"；修正之后它真的撞了。
- **1-8**：车被风举过坡沿，落到坡顶，然后**再从 4 米高的坡顶往前落** ——
  那一跳 6.9 m/s，超过 damageMin。

判据没错，关卡形状要和判据对齐（第 72 轮已经立过这条规矩）：

| 关 | 改法 | 结果 |
|---|---|---|
| 1-7 | 台阶从 col 13 提到 **col 9**，终点放在台阶顶上（col 14） | 无伤窗口 1.4~3.0（0.75 秒），不带岩种必死，带种子不按也必死 |
| 1-8 | 终点从 col 48 挪到**坡顶**（col 31） | 无伤窗口 3.75~6.0+（2 秒以上），不带风种必死 |

两关都是"车被顶上去就停在终点上"，不再需要落回地面。
判据没有为关卡让路，是关卡为判据让路 —— 这是第二次。

## 17. 第 79 轮：提示是假的，而且最具体的那一条根本看不到

改关卡改得凶的几轮之后，`HINTS`（手写中文句子）开始和现实脱节。
这一轮把"文案是否属实"做成可数的判据，抓到三类问题。

### 17.1 三类假话

**① 零件旧名。** 1-2 的提示写「打气筒要装在猪的后面」，
而那个零件第 71 轮已经改名叫**仙术机关** —— 玩家在托盘里找不到"打气筒"。
同一关还有「不用电池」，电池第 63 轮就删了（这一句是**正当**的否定用法，
见下）。

**② 地形尺寸。** 1-8 的提示写「终点在一道 2 米高的台子上」。
第 78 轮把终点从 col 48 挪到坡顶之后，实际爬升是 **3.85 米**，
而且它不是"台子"，是**一段缓坡**。1-7 写的「2 米高」实际是 1.19 米。

**③ 最严重的一条：第 4 层提示永远显示不出来。**
1-3 / 1-5 / 1-7 / 1-8 各有 **4 层**提示，而界面把层数**写死在 2**（第 3 层），
出现在四个地方：

```js
state.hintTier = Math.min(2, state.hintTier + 1);   // 点提示
const tier = Math.min(state.hintTier, 2);           // 画卡片
for (let i = 0; i < 3; i++) { ... }                 // 画层数点
const canMore = state.hintTier < 2;                 // 底部提示
```

而第 4 层恰好是**最具体**的那条（「成品：……」，写清了每个零件放哪）。
玩家翻到第 3 层看到的是"原理"，看不到"怎么做"。

修法：层数从 `HINTS` 自己数（`hintTierCount(lv)`），四处都改读它。
加一层提示不用改界面，也就不会再有"写了但看不到"的句子。

### 17.2 判据在写的途中坏了三次

`test_hints_truth.js` 的 A 组想做"提示里提到的零件名必须存在"，
连改三版**全部失败**，而且失败得很有教育意义：

| 版本 | 做法 | 结果 |
|---|---|---|
| 1 | `/[\u4e00-\u9fa5]{1,4}(筒\|轮\|框…)/g` 整段比对 | 「三块木框」「冰面上木轮」被判成不存在的零件 |
| 2 | 从最长尾缀开始试 | 冒出「这一关」「你的发动机」「位置很关」—— 「关」是"仙术机关"的末字 |
| 3 | 维护"历史旧名"表 | 但「不用电池」「不需要装马达」是**正当**说法，被判成旧名残留 |

**结论：中文没有词边界，通用分词在这个场景不可能可靠。**
与其留一条误报率 90% 的判据（真问题会淹在噪音里），不如换一条窄而准的：
维护一张历史旧名表，并且**旧名前面紧跟否定词就放行**。

D 组同病：第一版把 1-8 那句「这一关没有岩种 —— 只有风种」
判成缺陷，而那正是这关**最关键的一句对比提示**。同样加了否定词豁免。

第三条教训值得单独记：**判据自己坏掉时，它报的红和真问题的红长得一样。**
这一轮的第一版 A 组报了 25 条"缺陷"，其中 24 条是判据自己造的。

### 17.3 提示还有一条完全不可见

写测试时顺手发现的：`test_hint_tiers.js` 的 A 组第一版**自己模拟"点 N 次"**，
但模拟里仍然写着 `Math.min(2, ...)` —— 它量的是测试里写死的上限，
不是页面里的上限。于是产品改好之后它照样红。

修法：直接走页面自己的函数（`hintTierCount` + `hintFor`），
两者同源才是这条判据的意义。这条和"测试的夹具必须和产品同形"是同一个道理，
只是这次坏的是**被测对象的替身**而不是夹具的形状。

## 18. 第 80 轮：质心修正之后，手感还对不对

第 77 轮把转动从"绕局部原点"改成"绕真实质心"，并给接触加了杠杆分配。
那是根级别的物理改动，**姿态**（`test_car_stance`）已经证明对了，
但**手感**没量过：加速要多久、能跳多高、落地疼不疼。
这一轮把它们量出来、定成基线，防止以后再静默漂移。

### 18.1 六条基线（实测值）

| 组 | 量什么 | 实测 |
|---|---|---|
| A | 1-1 从静止到 3 m/s | **2.93 秒** |
| B | 平地喷气极速 | **12.00 m/s**（= maxSpeed） |
| C | 1.5 米自由落体后的回弹 | **0.000 米** |
| D | 2.5 米自由落体后的回弹 | **−0.043 米**（压进去一点，不弹） |
| E1 | 20° 坡下滑加速度 | **3.21**（理论 g·sinθ − μ_roll·g·cosθ = 3.37） |
| E2 | 0.2 m/s 残余 4 秒滚动 | **0.016 米** |
| F | 8 m/s 冲 20° 坡的最大俯仰 | **24.4°** |

### 18.2 三条判据是空转的，而且都是**反向验证**抓出来的

这一轮最花时间的不是量，是发现"量了的判据什么都没量到"。三处：

**B 极速**：第一版只写"没超过 maxSpeed"和"至少 8 m/s"。
把 maxSpeed 从 12 抬到 40，判据**照样绿** —— 因为它从没量出
"极速由 maxSpeed 决定"这件事。改成"极速必须落在 maxSpeed 的 92%~101%"。

**C 腾空**：第一版从 t=0 开始取 max，而车是从 0.8 米高处出发的 ——
于是峰值永远等于 **0.8（初始高度本身）**，腾不腾空都是 0.8。
把 liftMaxRise 抬到 12 照样绿。改成"先让它落下来，再量落地后的回弹"。

**E2 蠕行刹车**：试了**四次**都量不出它的独立贡献：

| 版本 | 场景 | 结果 |
|---|---|---|
| 1 | 0.5 m/s 切向 | 滚动阻力 0.22 秒停住，刹车多余 |
| 2 | 0.12 m/s 切向 | 滚动阻力 0.05 秒停住，刹车多余 |
| 3 | 0.12 m/s 竖直 | 车离地→重力拉回→落地弹 0.178 米，量到的是**回弹** |
| 4 | 0.2 m/s 差分（开/关刹车对比） | 开 0.0159 / 关 0.0003，方向还反了 |

根因算得出来：滚动阻力（`0.14 × 16 = 2.24 m/s²`）单独就能停住
一切 4 秒内滑动 < 9 m/s 的车，而蠕行刹车的窗口是 `spNow < 1.5` ——
**完全被包含**。两套机制做同一件事，平地上冗余。

这不是缺陷（冗余不伤行为），但它有两条后果：

1. 判据只能保护**行为**（低速残余会停），不能保护**某一段代码**；
2. 对应的反向验证（关掉 `creepBrake`）**必然不红** —— 那是真结论，
   不是判据空转。所以那条在 `_redproof_feel.js` 里标成 informational，
   并把这段推导写在旁边。

**这条值得单独记**：不是所有判据都能追到一行代码。
当两套机制覆盖同一行为时，"拆掉其中一套看看会不会红"这个方法本身就失效了，
得改用差分（关掉前后对比），而差分也可能因为幅度太小而量不出来。

### 18.3 又一次踩到反引号

`fix_feel_vacuous2.js` 是个**生成器**：它用模板字符串包着要写进
`test_feel.js` 的代码。而被写入的代码注释里有反引号（`` `roll = ...` ``），
于是生成器的模板字符串被提前闭合。

这是这个项目**第四**次踩同一个坑（前三次：`test_seed_fx` /
`test_challenge_bar` / `test_wind_fx`）。规矩早就写在
`docs/collaboration.md` 的「六个 headless 陷阱」里：
**模板字符串里不能出现反引号，注释里也不行**。

这次的处理是写了一个 `fix_backtick_bug.js`：扫描生成器里"既是注释
又含反引号"的行，把反引号换成中文引号，再用 `node --check` 验证语法。

## 19. 第 81 轮：1-6 那 17 次硬撞击是我自己造成的

### 19.1 先纠正上一轮的一个结论

第 80 轮我在八关手感扫描里写："1-6 是唯一一条手感数据异常的关：
最大离地 2.63 米、**17 次硬撞击**、俯仰 37°。"

这一轮查清楚了：**那 17 次是我的量法造成的假象。**

第 80 轮那个扫描脚本是手写的 `for` 循环逐帧 `step`，它**没有处理
`spec._drops`** —— 也就是说沙袋从来没被扔掉。于是车带着 3 个气球
一路飘到天上、反复磕天花板，撞出 17 次硬接触。

走 `R.simulate()`（它正确处理 `_drops`）时，硬撞击是 **0 次**，
`struct_hurt` 也是 0 次。

这条的教训和前面几轮是同一类：**量具必须走产品真实的那条路径**。
`simulate()` 里那段 `_presses / _drops / _pops / _seeds` 的时间轴
不是装饰 —— 它是"标准解"这个概念的实现。手写循环等于自己发明了
一个不扔沙袋的标准解，然后量它。

`test_lift_level.js` 的 E 组把这件事固化成两条断言：
E1 走 simulate 时 0 次硬撞击，E2 手写循环能复现 17 次。
两条都要有 —— 只留 E1 的话，下次有人再写手写循环还是会得到假数据。

### 19.2 那这一关到底有没有决策

1-6 教的是"气球给浮力、压舱石给配重"。既然数据没有异常，
真正该问的是：**如果怎么操作都能过，它就是动画而不是关。**

量出来的四件事：

| 组 | 量什么 | 结果 |
|---|---|---|
| A | 扔完 / 一个不扔 / 扔一半 | 只有**扔完**能拿三星（另两种 2 星通关） |
| B | 扔沙袋时刻从 0.5 扫到 3.0 秒 | 24/26 个采样点都能三星 —— **时机不构成门槛** |
| C | 1~3 气球 × 1~3 沙袋共 9 种 | **6 种**能通关（1 气球的全不行） |
| D | 沙袋数 × 扔的个数穷举 | 第三星**只在**"扔的个数 == 带的个数"时亮 |

结论是清楚的：这一关的决策在**构型**（挂几个气球）和**做完**（扔完），
不在**时机**。B 组窗口 2.4 秒、C 组 6/9 —— 这是一关"宽松但有边界"的设计。
不是卡帧操作，也不是放动画。

### 19.3 两条判据在写的时候坏了

**B2 净重转正后不该升** —— 实测 3 气球 3 沙袋仍然升了 7.5 米。
查下来是**算术**：质量 6.45 + 3×0.8 = 8.85，浮力 3×3.2 = 9.6，
净重 −0.75，**仍然是负的**。要让净重转正需要 4 个沙袋（3.15/0.8 = 3.94），
而这一关只发 3 个。

所以"3 气球 3 沙袋不飘"这个预期本身就是错的。改成量真正可预期的东西：
**挂沙袋会让车升得更慢**（10 米 → 7.5 米）。

**C 扔一个沙袋净重增加 0.8** —— 符号反了：`netMass = mass − lift`，
扔沙袋让 mass 减 → netMass **减**。同时 `dropSandbag` 返回的是
**boolean** 而不是 `{ok}`，判据写 `r && r.ok` 永远失败。

后者是第 79 轮那个病的同款（把返回值形状猜错），
再一次印证：**判据自己坏掉时，它报的红和真问题的红长得一样。**

### 19.4 顺带确认的浮力模型

| 挂法 | 质量 | 浮力 | 净重 |
|---|---|---|---|
| 0 球 0 袋 | 6.30 | 0 | 6.30 |
| 3 球 0 袋 | 6.45 | 9.60 | −3.15 |
| 3 球 3 袋 | 8.85 | 9.60 | −0.75 |

每个气球净贡献 −3.15 kg（质量 0.05 + 浮力 3.2），每个沙袋 +0.8 kg。
两个数都是玩家能自己算的 —— 这正是"可预期"的定义。

## 20. 第 82 轮：看门狗的两个阈值在结构上不可能失败

### 20.1 连着两轮犯同一个错

第 81 轮我手写循环漏了 `_drops`，量出 17 次假撞击。
第 82 轮一开始，我又手写了一份循环 —— 这次处理了 `_drops`，
**漏了 `_seeds`**。于是 1-7 / 1-8 的标准解在它眼里"从没升柱、风场从没触发"，
量出最小进展 −1.4 米，看起来像看门狗会误杀正确的打法。

教训不是"下次记得补上"，而是**这个循环不该有第二份实现**。
所以这一轮把 `opts.trace` 加进了引擎的 `simulate()`：

```js
var trace = opts.trace || null;
while (state.phase === 'run' && state.time < maxT) {
  ... 时间轴（_presses/_drops/_pops/_seeds 一份） ...
  step(state, dt);
  if (trace && state.car) trace.push({ t, x, y, left, goalX, air, result });
}
```

时间轴也抽成了 `buildActTimeline(spec, opts)` —— 所有扫描工具读同一份轨迹，
引擎怎么变它们就跟着变。E 组自证：开着 trace 跑，结果与时间必须完全一致。

### 20.2 然后发现"0 触发"是数学必然

| 关 | 标准解时长 |
|---|---|
| 1-2 | 2.95 s |
| 1-6 | 2.42 s |
| 1-4 | 3.75 s |
| 1-5 | 3.90 s |
| 1-7 | 5.68 s |
| 1-8 | 6.40 s |
| 1-1 | 6.85 s |
| 1-3 | **7.02 s** |

而 `progressWindow = 8`。**没有任何一局获胜的车能凑满一个完整的 8 秒窗口。**

于是"标准解 0 触发"是**数学上的必然**，不是安全属性。
证据：把 `progressGain` 从 2 抬到 **60**，所有判据照样绿 ——
那条断言量的根本不是 gain，而是"窗口凑不满"。

这正是第 80 轮"三条判据空转"的同款问题的第四次出现，
而且这次是**结构性**的：整个阈值从来没有可能作用在获胜局上。

### 20.3 正确的判据是结构性的

真正的安全属性：**W 必须大于任何可能的获胜时长**。

而"获胜时长"不能事先知道 —— 换个关卡、换个走法就会变。
所以这条属性只能**持续测量**：

```js
const maxDur = max(所有标准解的时长);   // 现在 7.02
chk('progressWindow 大于最长标准解时长的 1.2 倍', W >= maxDur * 1.2);
```

原来 `W=8` 对 `maxDur=7.02` 的余量只有 **0.98 秒（12%）**——
只要 1-3 稍微慢一点（玩家保守、将来关卡调长、物理再改一次），
看门狗就会开始误杀。这条断言第一次被写出来时就是红的。

### 20.4 W 提到 10

960 局随机扫描的取舍：

| W | 余量 | 误杀获胜 | 抓到失败 | 总共省 |
|---|---|---|---|---|
| 6 | **−15%** | 0 | 271/905 | — |
| 8 | +14% | 0 | 191/905 | **5 秒** |
| 10 | +42% | 0 | 18/905 | 1 秒 |

W=8 多抓的 173 局，**总共只省 4 秒**（平均每局 0.02 秒）——
这个阈值现在几乎不省任何时间了。

原因：它当初是为"车以 0.2~0.4 m/s 慢慢溜到墙前"设计的。
质心修正之后那种局基本消失 —— 905 个失败局里 **562 个是 `stuck`**
（5 秒就抓）。它现在的价值是"兜住极端情况"，不是"日常省时间"。

不误杀是硬约束，"多抓"是优化项。所以 `progressWindow: 8.0 → 10.0`。

### 20.5 顺手退场一个过期工具

`tools/sweep_watchdog.js` 有两个过期：
1. `KEYS = ['1-1','1-2','1-3','1-4i','1-5m','1-6']` —— 六关时代的手写表。

   它把 1-5m 的**正确判负**报成"标准解误杀 2"。
2. 自己手写的时间轴没有 `_seeds`。

改成直接指向新脚本，保留文件名（历史文档有引用），但不再是第二份实现。

### 20.6 调 W 牵动了两个硬编码

`test_progress_watchdog.js` 里有三处写死 `8`：

1. 断言"参数是量出来的那一组（8 秒 / 2 米）"→ 改成**区间**断言

2. 构造 `noGainFor = 6.0` 期望"还剩 2 秒"→ 改成 `W - 2`。

## 21. 第 83 轮：难度曲线，以及雷屏障的两处坐标原点 bug

### 21.1 难度不能用时长度

八关标准解时长 2.42~7.02 秒，看起来"差不多长"。但那量的是**标准解**，
也就是"已经知道答案的人"的成绩 —— 它反映的是关卡长度，不是难度。

难度是"**不知道答案的人**有多大机会蒙对"。那只能靠随机造法扫出来。

这一轮把随机造法扫出来的通关率当成难度指标：

| 关 | 随机通关率 | 平均时长 | 平均星数 |
|---|---|---|---|
| 1-1 | 16.00% | 7.60 s | 3.0 |
| 1-2 | 5.67% | 4.57 s | 3.0 |
| 1-3 | 7.00% | 7.26 s | 2.5 |
| 1-4 | 18.33% | 4.22 s | 2.8 |
| 1-5 | 25.33% | 5.56 s | 2.5 |
| 1-6 | 5.00% | 3.87 s | 2.0 |
| 1-7 | 3.00% | 6.40 s | 2.7 |
| 1-8 | 0.68% | 6.34 s | 2.7 |

前半段（1-1..1-4）平均 11.75%，后半段（1-5..1-8）平均 8.50%。
曲线是**下降**的（后面的关更难），这条现在有断言守着。

### 21.2 这个量具错了四次

| 版本 | 做法 | 结果 |
|---|---|---|
| 1 | 用标准解时长 | 只量了关卡长度 |
| 2 | randomBuild 不放种子 | 1-5/1-7/1-8 通关率 0% |
| 3 | randomBuild 不放伞/风之翼 | 1-8 仍然 0% |
| 4 | 触发时刻只采样 0.6~3.8 秒 | 1-8 的窗口是 3.75~6.0，几乎够不到 |
| 5 | N=240 + 触发范围 0.6~6.0 | 1-8 报 0.0% —— 而真实值 1.7%，240 局零命中的概率是 1.6% |

第 5 条是**采样量不足**：低概率的关在固定 N 下会假 0%。
修法是**自适应采样**：每关跑到"既跑够 300 局、又攒到 3 次通关"才停。

而自适应采样自己也有个陷阱：第一版只要求"攒到 3 次就停"，
于是 1-1 跑了 6 局就报 **50%**（真实 16%）——
**早停总是停在运气好的那一侧**。必须同时要求最小局数。

顺带把随机造法抽成 `tools/lib/random_build.js`（全项目唯一一份）：
零件池从 `level.partsBox` 读，能放的都会放到。
这是连着第三轮"某个脚本另写了一份随机造法/时间轴然后漏了东西"，
所以这次不给它第二次机会。

### 21.3 顺带挖出两个真 bug：雷屏障的坐标原点

1-5 有雷屏障（col 20，4 米高）。第 72 轮验过"不带雷种被顶住、带雷种冲过去"。
随机扫描却有约 4% 的局**不带雷种也通关**。

逐帧查下来是两个独立的 bug，而根因是同一个：

> `car.x` 是**网格锚点**，不是车体几何中心。
> `buildVehicle` 里的 `hull` 是相对锚点算的，所以 **`hull.maxX` 可以是负数** ——
> 单框车（放在 col 1）的包围盒是 `[car.x−2, car.x−1]`，`maxX = −1`。

**① 鼻子判错**：`var nose = car.x + car.hull.maxX`
对单框车算出来是 `car.x − 1`，指向车心**左边**。于是
`nose < br.col` 在车已经压在屏障上时仍然成立，判定被整段跳过。
实测 1-5 的随机车里 **190/300 辆**都是 `maxX ≤ 0`，全部能穿。

**② fromLeft 判错**：`var fromLeft = car.x < br.col + 0.5`
实测 t=7.450 `car.x = 20.944`（车体 `[18.94, 19.94]` 全在屏障左边），
因为 `20.944 > 20.5` 被判成"从右边来"，走进右分支：

```
car.x = br.col + 1 − hullMin + 0.02 = 20 + 1 − (−2) + 0.02 = 23.02
```

**一帧瞬移 2.076 米穿过去。**

两处都改成用真实包围盒：`hullL / hullR / hullC`。
修完之后"无过屏障手段的车出现在屏障右侧"从 190/300 降到 **0**。

### 21.4 而且揭穿了一个设计假设

修完仍约有 1.2% 的随机局"不带雷种也能过"。查下来**那不是 bug**：
1-5 的零件箱**同时发风种 + 伞和雷种**，屏障有两种过法 ——
冲过去（雷种）或飞过去（风种 + 伞）。屏障顶 9.93，车 y≈7.0，
需要抬升 1.93 米；伞给 2.72 米，够。

所以第 72 轮那句「1-5 必须有雷种」**是不准确的**。
现在它是可数的判据（`test_barrier.js` 的 C 组）：
"风种 + 伞也能过屏障" 被显式断言，如果哪天有人削弱伞，
这条会红，提醒他这是一个**设计变更**而不是意外。

### 21.5 一条判据的阈值也写错过

D 组第一版写"单帧位移 ≤ 0.6 米"，实测最大 0.637 —— 但那不是瞬移：
它是"车已经和屏障重叠 0.637 米，被推出来"的**解算位移**，
和"穿过"性质完全不同。

所以判据改成量**结果**：没有过屏障手段的车绝不该出现在屏障右侧；
位移只用来兜住数量级明显不对的情况（> 1.5 米）。

## 22. 第 84 轮：randomBuild 有格子冲突（又一个量具 bug）

### 22.1 症状

上一轮说"下一轮把 1-8 的 0.68% 提上来"。这一轮先量它到底卡在哪，
结果发现**那个 0.68% 本身就是假的**。

400 局随机造法里，**161 局（40%）有零件被静默覆盖**：

```
randomBuild 把 propeller / jet / pump / umbrella / wind_wing / balloon
全放在**行 3** 的同一批候选格 [3, 1+rnd(nFrame)] 上，
而 applySpec 是"后写覆盖先写"。
```

对 1-8 尤其致命：那一关只发 1 个 propeller 和 1 个 umbrella，
两者撞同一格时**伞被覆盖** → 风场托不动 → 必然失败。

所以第 83 轮量到的"1-8 只有 0.68%"里有一大半是**量具造成的**。

### 22.2 修法与效果

每一行维护一个"已占用的列"集合，只从空格里挑；零件多于格数时**跳过**
而不是覆盖。

修完之后：

| 关 | 修前 | 修后 |
|---|---|---|
| 1-1 | 17.00% | 27.33% |
| 1-2 | 8.00% | 12.67% |
| 1-3 | 6.67% | 9.33% |
| 1-4 | 24.67% | 25.67% |
| 1-5 | 25.00% | 27.33% |
| 1-6 | 5.33% | 5.00% |
| 1-7 | 3.67% | 4.00% |
| 1-8 | 1.33% | 1.00% |

**八关全部上涨 30~60%**（1-6/1-7/1-8 在噪声内）——
也就是说第 83 轮那张"难度曲线"整体是被低估的。

### 22.3 1-8 到底是什么样的难度

格子冲突修好之后重新拆：

```
600 局随机造法：
  缺驱动件 319 局（53%）  ← 最大的筛子
  缺吃风件 167 局（28%）
  缺风种   142 局（24%）
  三件套齐 134 局（22%）→ 通关 8.2%
  三件套齐 + 触发 ≥3.6s 51 局 → 通关 17.6%
```

结论：1-8 的难度**几乎全部来自"凑齐三件套"**，不是操作时机。
凑齐之后只要不按太早，成功率就上来一个量级。

这是**设计选择**：1-8 是一关"配置题"。而且 22% 的随机局能凑齐，
说明它不是"随机探索够不到"。

这一轮把它写成四条判据（`test_1_8_structure.js`）：

| 组 | 判据 |
|---|---|
| A | 三件套齐的通关率 ≥ 全随机的 3 倍（确实是配置门槛） |
| B | 随机局里 ≥ 10% 能凑齐三件套（不是够不到） |
| C | 三件套齐且触发 ≥3.6 秒时通关率 ≥ 10%（凑齐之后真能过） |
| D | 最后两关（1-7 / 1-8）是八关里最难的两关 |

D 组第一版写的是"1-8 是唯一最难的一关"，实测 **1-7 更难**（2.67% vs 1.00%）。
那不是缺陷 —— 两关都是种子关，是这一章的收尾。
判据改成量那个真正成立的性质：**最后两关是最难的两关**。

而且 D 组第一版只跑 120 局/关，于是 1-7 报 0.8%、1-8 报 2.5% ——
低概率关在 120 局下方差极大（第 83 轮已经踩过这个：N=240 会让 1.7% 的关假报 0%）。
改成自适应采样（至少 300 局）。

### 22.4 randomBuild 的四次翻车（更新）

## 23. 第 85 轮：回到画面 —— 1-3 的洞穴暗到看不清

### 23.1 为什么这一轮回到画面

**① 1-3 的洞穴配色 68.1% 的像素亮度 < 40。** 对照 1-1 是 3.6%。

`cave` 那一套从 rock 到 jungle **全是 0.05~0.20 的亮度**：

rock [58,74,84]   skyTop #0d1a22   skyMid #132530   skyLow #1b3340
hill #0b1822      jungle [#15302a, #102420, #0b1a17]

那一帧是黄昏 + 视野压低，画面本来就偏暗（均值 51）。
判据改成"暗场景（均值 < 70）放宽到 σ ≥ 20"。

## 24. 第 86 轮：HUD 遮挡 → 挖出 1-6 的终点放错了

### 24.1 HUD 遮挡测试的第一版，量的是一个不会更新的量

`test_hud_occlusion.js` 第一版在 `Runtime.evaluate` 里用 `RAP.step()` 连跑
40 秒，每帧读 `state.camLive` 算车的屏幕位置。

但 `camLive` / `camState` 是**渲染层**在 `drawRun()` 里更新的：

```js
const targetX = car.x + 2.0 + Math.min(1.6, spd * 0.14);
const targetY = Math.max(car.y, surfaceY) + 1.5;
cs.x += (targetX - cs.x) * k;
```

而 `RAP.step()` 只推进**引擎**，不渲染。于是整个 40 秒循环里
`camState` 一次都没动（还停在初始的 `{x:0, y:0, zoom:1.7}`），
算出来的车屏幕位置完全错位 —— **1-6 报的"车被盖 75%"就是这么来的**。

这是第 81/82/84 轮同一个病的第四种形态：
**量具读了一个产品没有更新的量**。

第二版改成按渲染层的同一套公式算镜头，并加了一条**视觉自证**：
真的渲染一帧、截图、在车所在的屏幕区域里数木色像素（实测 50.4%）。

### 24.2 然后发现 1-6 的终点在坡脚之前

1-6 的地形：col 0~15 缓下坡，col 16 起是**6 米上坡**（3.95 → 9.97 @ col 24）。
而 `goal = col 15` —— 正好在坡脚**之前**。

实测标准解 **2.42 秒**就到终点，那道 6 米上坡一次都没用上。
也就是说这一关教的是"气球给浮力"，玩家实际上只需要一路开过去。

扫描终点位置 × 气球数：

| goal | 无气球 | 1 气球 | 2 气球 | 3 气球 |
|---|---|---|---|---|
| 15 | fail | fail | win@3.9s | win@2.4s |
| 18 | fail | fail | win@5.0s | win@4.3s |
| **22** | **fail** | **fail** | **win@5.4s** | **win@4.9s** |
| 24 | fail | fail | win@7.2s(x=39) | **fail**（飞过头） |

选 **col 22**：无气球和 1 个气球都过不去（机制必须用上），
2~3 个气球都能过且**落在终点上**，标准解仍然三星，
第三星「沙袋全扔」仍然只有扔完才拿得到。

### 24.3 改地形时把行号算错了

终点挪到坡上之后，标准解在 t≈2.5 撞出 `touch lvl=3 v=5.3` 掉 1 点耐久。
根因是坡太陡：col 15→18 是 **41° / 47° / 52° / 56°**，
车以 6.5 m/s 冲上去前轮撞坡面，够到 `damageMin = 4.5`。

第一次改缓坡时，我用 `row = H-1-round(y)` 换算行号。
但 `makeTerrain` 的约定是 `高度 = rows - topRow`，也就是 `topRow = rows - 高度` ——
我多减了 1，**整张地图抬高了一米**：

```
旧 surfaceY(0..8) = 4.000 4.000 3.999 3.995 3.990 3.960 3.883 3.731 3.174
新 surfaceY(0..8) = 5.000 5.000 5.000 5.000 5.000 5.000 5.000 5.000 5.000
```

起点区被填平了，`test_parts_connected` 的 propeller ↔ 木框接缝**
从 100% 掉到 15%**。那一红不是"零件没连上"，是**地形被改坏了**。

改成 `topRow = H - round(y)` 并**保留 S / E / B 标记**之后，
坡变成 16°~31°，标准解 3.02 秒三星、**0 次掉耐久**，七条相关测试全绿。

### 24.4 三条判据在同一轮里被改软

改关卡形状会牵动一批「按旧形状定的」判据。这一轮改软了三条，
每一条都记了原因：

| 判据 | 为什么改 |

## 25. 第 87 轮：HUD 遮挡是恒等式 —— 第五种空转判据

### 25.1 逐帧量出来的 0.0% 是几何，不是安全

上一轮加了 `test_hud_occlusion`，B 组逐帧量"车被 HUD 盖住的比例"，
八关全是 **0.0%**。

查下来那是**恒等式**。镜头目标是：

```
targetX = car.x + 2.0 + min(1.6, spd × 0.14)
targetY = max(car.y, surf) + 1.5
```

镜头跟着车走，所以车在屏幕上的位置是固定的：

```
cx ≈ 640 − (2.0…3.6) × s
cy ≈ 360 + 1.5 × s        s = 32 × zoom ∈ [44.8, 59.2]
→ cx ∈ [427, 550]，cy ∈ [427, 449]
```

而 HUD 最下面一块的下沿是 **232**。间隙 163 px。
**这条判据结构上不可能失败** —— 它量的是几何，不是产品。

这是"空转判据"的第五种形态（第 80 轮三条、第 82 轮看门狗）。

### 25.2 换成结构性判据

真正的安全属性是：**车的屏幕驻留区与 HUD 之间要有余量**。
`test_hud_geometry.js` 把它写成一条纯几何断言，而且**带自证**：

| 组 | 判据 | 实测 |
|---|---|---|
| A | HUD 下沿与车驻留区至少留 100 px | **106 px** |
| B | 车驻留区完全在画面内 | x 到 669（宽 1280） |
| C | 驻留区与 5 块面板都不相交 | 全部避开 |
| D | **自证**：HUD 下移 300 px 时 A 与 C 都红 | 间隙 −194 px，相交 2 块 |

D 组的自证是关键 —— 它证明这条判据**能失败**。
`test_hud_occlusion` 的 B 组降级成记录项，注释写明为什么。

### 25.3 顺带查清 1-6 的 391 帧是假的

第一个版本的 B 组虽然结论"0%"是对的，但过程是错的：
它手写 `RAP.step` 循环，**没处理 `_drops`** —— 沙袋从未被扔掉，
车被 3 个气球一路飘到 x=46（cols=44，出界）。那 391 帧里后半段
量的是"车已经飞出地图"的画面。

这是第 81/82/84/86 轮同一个病的**第五次**。修法：让**引擎**跑完并录轨迹
（`simulate(..., {trace})`，第 82 轮加的），测试只读轨迹再按公式算几何。
新增 E 组专守这条：

```
E 八关标准解都没有跑出地图（否则量的是假画面）
```

### 25.4 `__lockCam` 只锁镜头，不锁物理

同一轮里视觉自证 D 组两次跑报"车中心 (1134,453)"和"(1009,453)"。
查下来 `__lockCam` **生效了**（`camLastDraw` 等于锁定值），
但 rAF 循环里仍在 `RAP.step(state.run, 1/60)`：

```
700ms   carX=12.59   camLastDraw=8.978
1400ms  carX=19.11   camLastDraw=8.978
```

锁的是镜头，车还在跑。所以"设好状态抓一帧"这种做法，
没有对应的物理开关就只能靠 sleep 猜帧数。

加了同级钩子 `state.__freezeRun`（渲染层读它决定是否跳过这一帧的 `RAP.step`）。
加了之后 D 组三次连跑都是 **(522,449) / 37.4%**，
`test_legibility` 也从"最低 29.9 / 有时 3"变成稳定的 **24.5**。

新加的 `__` 字段被 `audit_state_fields`（第 57 轮建的）抓住了 ——
那是它**第二次**抓到新代码，第一次是第 85 轮的配置目录泄漏。
两个守卫生效了。

### 25.5 顺带量了落点可见性

镜头公式 `targetY = max(car.y, surf) + 1.5` 有个真问题：
车飞起来时镜头跟着车上去，**地面会掉出画面**。
这个游戏是骑车上坡 / 气球飞起来的，落点可见性是核心信息需求。

`test_ground_visible.js` 逐帧量"车正下方那一列的地面在屏幕上的 y"：

| 关 | 离地帧 | 地面出画 | 车出画 |
|---|---|---|---|
| 1-1 | 411 | 0 | 0 |
| 1-6 | 181 | 0 | 0 |
| 1-8 | 384 | 0 | 0 |

八关全部 0 —— 因为 `+1.5` 米的下偏正好把地面留在画面下部。
这是**量出来的结论**，不是设计时算过的，所以值得钉住。
